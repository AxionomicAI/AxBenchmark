# Same-model harness comparison and API access routes

Status: binding implementation supplement, requirements **R192–R194**. Build this feature from scratch with the current contracts; no older-installation migration or obsolete record-format support is required. This document specifies implementation work, not working integrations or a passing provider matrix.

A user selects one exact model, one explicit reasoning-effort contract, one benchmark revision and a trial count, then compares that choice across the supported harness registry: **Claude Code, Codex CLI, Grok CLI, Pi, Cursor CLI and OpenCode**, in that order. OpenRouter and LiteLLM are selectable API access routes, including an explicit LiteLLM → OpenRouter chain. They are neither additional harnesses nor additional scorers. “OpenAI” in this feature means customizing **Codex CLI**; it does not add a standalone direct-API competitor.

This extends [M04 catalog](reference/modules/04-model-catalog.md), [M05 adapters](reference/modules/05-harness-execution-isolation.md), [M07 configuration](reference/modules/07-run-configuration.md), [model variants](MODEL-VARIANTS.md), [statistics](BENCHMARK-STATISTICS.md) and [results storage](RESULTS-DATABASE.md). It preserves benchmark modes, isolated baseline copies, fresh task sessions and mandatory task commits. Existing individual configurations remain available; matrix creation is an additional setup path.

## Product behavior and comparison scope

The initial matrix always contains all registry harnesses, including missing installations and incompatible routes. The default is `strict`, selecting all six with `jobs=1`; strict mode requires this existing single configuration slot. Explicitly reviewed exploratory mode may use other existing concurrency settings. Each selected cell expands into exactly one ordinary competitor ConfigurationId with the same positive trial count; all generated entries launch together under one RunUid. No extra planner, task, retry, repair pass or grader is synthesized. Independent repeated matrices receive new RunUids; equal labels never merge them.

`strict` requires every selected cell to be ready against the frozen common controls before launch. An explicitly chosen subset is allowed but remains labelled **Partial harness coverage (N/6)**, with all omitted/blocked rows and their reasons retained. There is no “run the compatible ones” implicit filter. `exploratory` allows disclosed model/effort/backend comparison uncertainty; it still requires qualified execution, tool, isolation and headless compatibility. Unsupported transport or an unusable model cannot be bypassed by choosing exploratory.

An unavailable cell creates no fake trial, zero quality grade, failure score or rank. Once a ready cell launches, genuine execution failures and missing trials follow existing M02/M06/M08 rules; they cannot be relabelled unsupported to improve the comparison. A stopped or failed cell retains every expected trial. Changing selected harnesses, routes, model, effort, controls or trial count after review creates a new preview; after freeze it requires a new run.

The measured variable is the harness, including its native instructions, tool descriptions, orchestration and compaction behavior. Identical provider settings do not make the internal conversations or reasoning traces identical. Keep the exact benchmark prompt/specification bytes and captured baseline common; record observable system/tool differences and unexposed portions through [context monitoring](CONTEXT-MONITORING.md). Do not rewrite native harness prompts into a common invented agent or ask a model to prove its identity.

## Versioned identity and public contracts

M04 publishes the following immutable DTOs through Bootstrap before consumers start. IDs identify records; canonical digests identify their sanitized contents. Updates create versions, never mutate a frozen launch. Local secret locators are excluded from portable snapshots and digests; account fingerprints and credential presence are non-secret evidence.

A common model-binding target fixes canonical upstream semantics; each cell resolves its own harness-selectable binding and effort mapping to that same target. Do not force one client alias across all wire protocols.

M07 `ConfigEntry` adds optional `access_selection: RoutedAccessSelectionV1` containing exact profile, model-binding, effort-contract and harness-mapping refs. Its ordinary `model_id` must equal the binding's harness-selectable ID; conflicting duplicated settings are validation errors, not precedence rules. FrozenLaunch, InvocationRequest and SelectionEvidence carry the plan/ref; existing direct-provider configurations remain valid without `access_selection`.

Protocol values are explicit: `anthropic_messages`, `openai_responses`, `openai_chat_completions`, or a separately versioned supported dialect. HTTP success on one is no evidence for another. Discovery catalogs are metadata, not authentication, billed usage, model execution or verified tool support.

## Common controls, effort and runtime evidence

The common-control digest includes exact template SHA/baseline, upstream model/revision/variant, inference deployment/tier/region where material, ordered route/provider policy, effort semantics and reasoning/output budgets, required sampling controls, environment policy, machine snapshot, concurrency/resource policy, trial count, timeout, verification policy, grading backend/group/rubric and weights. Unknown required controls do not match one another. Native tool/prompt/compaction differences are named harness effects; unsupported adjustable controls and protocol translation differences appear as limitations.

A different client wire protocol may be necessary for each harness. Record both protocols and their translation paths while holding the effective upstream model, effort and route policy fixed. A documented exact mapping may satisfy the effort contract; an approximate conversion from a level to a budget cannot. If such conversion is intentionally benchmarked, the result is exploratory. Reasoning summaries, returned reasoning text and actual reasoning-token counts are observations, never proof of equivalent internal effort.

Default `inference_scope=all_competitor_inference` covers main, helper, subagent, summarization/compaction and other model calls attributable to the coding harness. Required model/effort/route controls must apply throughout that scope. Native helpers may be disabled only through qualified controls, or pinned to the same contract. An unavoidable different helper model, effort reset, inaccessible request roster or unobservable helper binding makes strict comparison unavailable; exploratory results explicitly disclose the scope gap. Users may select `primary_model_only` only in exploratory mode, with helper models/settings separately recorded and all their attributable usage still counted.

Readiness requires installed adapter/route qualification and a verified fixed model/effort mapping, but does not claim that future requests have already run. At runtime retain actual per-request coverage and enforce the frozen contract. Complete, consistent observations produce `confirmed`; a frozen declaration without execution evidence remains `declared` or `unverified`. Strict **launch intent** alone never labels the finished data a confirmed same-model comparison.

Known model/variant mismatch follows existing model-rejection/exclusion handling and stops further work for that configuration. A changed provider route, ignored/dropped effort, mixed helper identity or conflicting observation records a typed comparison mismatch and prevents confirmed matching; use the frozen fail-closed stop policy for that configuration. Retain measured work/cost already incurred and original expected trials. Do not invalidate the common template, silently switch provider, retry with another effort, or repair the mismatch by relabelling historical facts.

## Access profiles, routing and isolation

Profiles apply to explicitly selected roles (`competitor`, `planner`, `harness_judge`) independently. A competitor profile change does not change a judge or planner selection. Generic OpenRouter/LiteLLM API availability does **not** make [System One decision grading or context classification](DECISION-ENGINES.md) ready; those retain their separate profile/dialect/capability gates. Human judging requires no API access profile.

For strict comparisons, disable model fallback, dynamic/automatic model selection, provider load balancing and parameter dropping unless a frozen policy proves that every possible route has the same required deployment and semantics. The initial implementation admits a single pinned upstream deployment per strict cell. Freeze model alias resolution and gateway configuration evidence; aliases such as “latest” without a pinned resolved revision cannot establish strict identity.

OpenRouter documents provider pinning/fallback controls and `require_parameters`; exact endpoint slugs distinguish regions/variants. Require the selected protocol/configuration mechanism to actually transmit or enforce those restrictions. A policy that exists only in the UI is not applied. The default router may ignore unsupported parameters, so its success response alone cannot prove effort preservation. [OpenRouter provider routing](https://openrouter.ai/docs/guides/routing/provider-selection)

OpenRouter's effort/budget mapping is model-dependent. Retain the actual native upstream value and any output-limit dependency; do not infer equivalence from the shared `reasoning` field. [OpenRouter reasoning controls](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens)

LiteLLM can discard unsupported fields when `drop_params` is enabled and can configure provider/model fallbacks. Strict qualification must establish that the selected deployment preserves the required fields and routing; a user-entered alias or unavailable gateway configuration leaves those controls unverified. A benchmark must never edit a shared proxy's global configuration. Explicit LiteLLM → OpenRouter profiles retain both policy layers and their separately scoped credential boundaries. [LiteLLM parameter dropping](https://docs.litellm.ai/docs/completion/drop_params), [fallbacks](https://docs.litellm.ai/docs/proxy/reliability), [OpenRouter provider](https://docs.litellm.ai/docs/providers/openrouter)

M05 renders only benchmark-owned ephemeral environment/settings through its existing isolation service. User global settings, login state, shell profiles and running gateways remain unchanged. Required credentials are resolved immediately before spawn, passed only to the intended client endpoint, and scrubbed from argv displays, generated public config, logs, errors, raw observations, SQLite, ZIPs and reports. Private temporary material has restricted permissions and cleanup/recovery ownership. A missing credential never falls back to a personal subscription or another provider.

Validate endpoint schemes/origins and reject credentials in userinfo/query strings. Use TLS for nonlocal credential-bearing routes; explicit loopback HTTP may serve an already configured local gateway. Never send provider credentials through redirects to another origin. No automatic installation, login, proxy startup, model download/loading or arbitrary gateway script execution is part of setup. Metadata inspection is explicit and makes no inference call.

Locality records gateway location and actual inference location separately: `local | remote | mixed | unknown`. A loopback LiteLLM server forwarding to a paid remote model is remote inference with local gateway overhead. It is not `LOCAL` billing, a free model, or exempt from existing trial-budget warnings. Unknown upstream locality receives conservative resource/budget treatment; gateway placement cannot bypass the existing measurement-admission rules.

## Existing agent aliases and launcher profiles

A user may explicitly inspect, register and select an independently supplied local agent profile. The user-provided name **`claudeg`** illustrates a named Claude Code launcher only. Its private configuration is not product configuration, a bundled registration, a default, a runtime dependency or a source for test fixtures; this example authorizes no reuse or automatic inspection of that configuration. The launcher is distinct from an API access profile, a gateway model alias and a model variant. A named Claude Code profile remains **Claude Code**, not a seventh harness. A harness-comparison cell may select one existing profile for that harness; ordinary configurations may compare several profiles of the same harness as separate ConfigurationIds. Such a comparison exposes the profile as an additional treatment and cannot claim that only the harness changed when their behavioral controls differ.

M04 publishes these contracts; local resolution bindings remain private machine configuration, separate from sanitized retained snapshots:

| Contract | Required fields and invariants |
|---|---|
| `ExistingAgentProfileRef` | Stable profile ID, positive version and canonical sanitized snapshot digest; display alias is never its key. |
| `ExistingAgentProfileV1` | Ref, display name, owning harness/distribution, registered source kind, sanitized source description, executable identity, ordered accepted argv/env/settings declarations, settings-source precedence, asset digests, role permissions, inspection evidence and observation time. Private source paths and credential resolution bindings are local-only. |
| `ExistingAgentProfileInspectionV1` | Inspection ID, parser/adapter version, source and dependency digests, accepted declarations, redacted credential-reference presence, unresolved expansions, control conflicts, required behavioral assets, isolation qualification and typed limitations. Inspection does not invoke the agent or certify served model/effort. |
| `ResolvedExistingAgentPlanV1` | Exact profile/inspection refs, `treatment: existing \| clean`, inherited declarations, explicit reviewed overrides and their provenance, sanitized effective-control digest, resolved model and any applicable access/effort-contract refs, isolated asset/config plan and qualified adapter-owned headless invocation. No executable shell text or secret value is a portable field. |

`ExistingAgentSelectionV1` contains the profile ref, treatment and reviewed override-set ref; `ConfigEntry` gains optional `existing_agent_selection: ExistingAgentSelectionV1`. M07 binds it to the selected harness and explicitly selected role; FrozenLaunch, InvocationRequest and SelectionEvidence retain the resolved plan reference. If both this selection and `access_selection` are supplied, every duplicated model, route and effort control must resolve consistently before launch. The profile does not implicitly apply to planners, harness judges or decision engines. An independently selected harness-review profile/treatment/effective digest enters JudgeGroup identity, so additional reviews using a different profile cannot share a group by label alone; human and System One group branches are unchanged. Planner provenance remains in its own M16 PlannerRecord scope, not a fabricated benchmark run. Competitor alias labels and profile metadata stay outside blinded judge inputs. No new process launcher or scoring path is introduced.

Discovery is a static read of an explicitly selected source. For an ordinary alias, accept only a qualified grammar of environment assignments followed by a known executable and literal argument vector, with allowlisted literal/path/environment-reference expansion. Parse relevant definitions without sourcing the shell startup file; never evaluate command substitutions, shell operators, redirections, arbitrary functions or scripts. Environment credential references remain private unresolved bindings until the existing spawn-time resolver needs them. Reject ambiguous/redefined/cyclic aliases or missing dependencies with precise remedies. Dynamic wrappers return `unsupported_dynamic` unless a separately reviewed structured registration and qualified adapter can preserve their declared behavior; inspection must not execute them to discover what they do.

Raw source fingerprints used for local drift checks remain local. Portable hashes cover sanitized approved declarations and non-secret assets; never hash credential values or include credential locators in profile identity. Inspection logs/errors/previews redact before publication and never dump the source file or alias expansion. Only allowlisted environment controls are inherited, not the whole interactive shell environment.

The engine may run noninteractively and cannot assume it inherits shell aliases. Registration compiles accepted declarations into structured argv/env/settings through the existing harness adapter. Execution uses the resolved underlying binary and the adapter's exact-version task prompt, headless output, fresh-session, deadline and workspace controls. It never runs the alias through `sh -c`, starts an interactive login shell or substitutes another harness. Installed executable identity, source/settings/asset digests and local secret availability are revalidated before freeze; changes produce `stale` or a typed blocked reason and zero spawn. After freeze each task uses the captured treatment and detects drift in any remaining external dependency before launch.

The default `existing` treatment preserves the accepted current behavioral settings, model/effort/route declarations, instructions, plugins and other qualified assets. It means reproducing a captured configured agent under the benchmark's fresh-session and isolation rules, not resuming personal history. The preview enumerates the required benchmark adaptations, including ephemeral config paths and task input, separately from user overrides. `clean` is an explicit transformed treatment with a reviewed keep/remove list; it must never silently replace existing behavior or be labelled exact existing-profile reproduction.

Never copy the entire profile/home directory. Copy only qualified configuration and declared behavioral assets, with content digests and safe relative bindings; exclude auth stores, sessions, project history, caches, logs, sockets and unrelated files. Secret references use the private resolver. Create writable config/state/cache paths per invocation and leave the source profile unchanged. A plugin, hook, helper or setting with unisolatable implicit absolute-path writes blocks profile compatibility; omission or redirecting behavior without an explicit reviewed transformation is not a remedy. Executable assets require declared capabilities and role-policy qualification; registration never installs or updates them. A profile cannot weaken mandatory commits, workspace isolation, fresh sessions, grader read-only rules or consent boundaries.

Preserve every inherited value and override origin. If a profile requests another model, effort, route or required shared control, the preview blocks until the user explicitly chooses **Use profile values** (revise the common comparison target and revalidate every selected cell) or a reviewed **Benchmark-only override** (create a transformed effective snapshot while retaining the source declaration). An ordinary individual configuration may adopt profile values without changing other configurations. Neither choice edits the alias or source settings. Unknown or ignored fields remain declared/unverified; successful execution, a setting name or a large requested number cannot establish model capacity or effective support. Preserve simultaneous credential declarations: coexistence alone is not a conflict. Unresolved credential behavior required for route qualification must be inspected or explicitly resolved in the reviewed treatment; never silently discard a mechanism or fall back to personal login.

Optional opaque/ignored settings alone do not block an ordinary existing-profile benchmark once required execution, route and isolation gates pass. With `HarnessDefault`, the adapter adds no effort override and retains captured profile declarations; display **Inherited from profile (declared)**, not unset or verified. Strict same-model/effort comparison still requires a qualified `Contract(ref)` mapping and complete required-control evidence. A known model mismatch, required-control conflict or unavailable isolation remains blocking regardless of optional-setting policy.

## Readiness, freeze and lifecycle

| Cell state | Meaning and permitted action |
|---|---|
| `ready` | Installed execution/route qualification and owner readiness pass; strict also has an exact verified common-control mapping. Review/launch permitted subject to fresh revalidation. |
| `blocked` | Known unavailable requirement, missing installation/credential/model, unsupported protocol/effort, isolation failure or policy conflict. Edit/remedy or explicitly deselect; zero spawn. |
| `unverified` | Required support/binding evidence is absent or applicability unknown. Inspect/qualify or explicitly use exploratory only when execution safety/transport/tools are already qualified. |
| `stale` | Profile, alias mapping, gateway config, catalog, installed version or other preview input changed. Refresh review; previous preview cannot launch. |
| `not_selected` | Explicitly omitted from this plan, retaining its last assessed capabilities and exclusion reason. Never hidden or counted as executed. |

Readiness reasons use typed paths and remedies, including `access_profile_missing`, `credential_missing`, `protocol_unsupported`, `distribution_unverified`, `model_binding_unverified`, `effort_unsupported`, `effort_mapping_unverified`, `routing_uncontrolled`, `helper_scope_unverified`, `gateway_config_changed` and `comparison_controls_differ`. Preserve existing owner errors rather than wrapping away their evidence. Endpoint unavailable/auth rejected/rate limited are distinct from unsupported protocol.

Matrix preview performs owner-backed reads, not model discovery/authentication calls as a side effect. Explicit metadata inspection may read supported model/config/status endpoints without inference. Installed transport/tool conformance tests are separately authorized diagnostics, scoped outside benchmark results and competitor accounting. The existing M03 default-model auth diagnostic remains unchanged; it cannot certify an explicit-model route merely by succeeding.

M03's separate `environment.qualify_route(RouteQualificationPlanV1) -> JobRef` requires explicit bounded probe consent through the existing diagnostics action policy. It freezes the requested model, effort and route rather than omitting them. M05 runs a fresh disposable session with a fixed benign read-only fixture tool, no workspace/user-file access, no shell/network tools and no arbitrary user prompt. Demonstrate a model tool call, its correlated fixture result and completed streamed continuation; fail qualification if the installed harness cannot establish these controls. This operation reuses process isolation, deadlines, cleanup and resource leases; it creates no benchmark result or score. Extend the existing `DecisionResourceLease` operation union with `route_qualification{job_id, verification_id, plan_digest, invocation_id?}`; M03 acquires this branch for actual local/mixed/unknown inference and records M10 `RouteQualificationObservationV1` through `RouteQualificationObservations.record`. No `DecisionCallId`, `ResultId` or `TrialRef` is invented. `VerificationScope.kind=route_qualification` retains the plan digest; default auth keeps kind=default_auth. Diagnostic accounting/route evidence stays in existing M03/M05/M10 journals rather than result-only SQLite rows.

Qualification bounds client invocations, wall time, emitted request/output limits and every exposed upstream attempt, including retries and discarded responses. Enforce gateway attempt/charge caps when the route exposes them; otherwise disclose unknown internal retry/charge coverage and never claim an enforced provider-side cap. Known unbounded active retry policies fail admission. Missing internal telemetry alone does not fail transport qualification, but cannot supply missing evidence for confirmed comparison or complete accounting. There is no second benchmark retry loop. Charge all calls to `verification`, retain route-specific prices/unknown cost, and settle possible local inference before releasing the shared resource lease. Consent to one probe is not consent to automatic future probes after a profile/version changes. Metadata checks and navigation remain free of inference calls.

M07 uses the existing expected draft revision and review digest. Resolve each selected cell, capture a coherent publication/catalog/capability view, then revalidate profiles, aliases, gateway evidence and effective policy immediately before the existing immutable launch transaction. No cells publish a launch before all selected cells pass. Gateway inability to expose/check its effective config is a limitation, not permission to manufacture a matching digest.

After freeze the ordinary M11 scheduler operates on the generated entries. Strict same-model comparison uses jobs=1 and no overlapping competitor windows; users may deliberately change concurrency in exploratory mode with the resource policy visible. Freeze selected registry order and retain actual timestamps/queue delays. Use the existing scheduler contract: a configuration holds its slot across its sequential trials; this feature introduces no interleaved trial rotation or statistical randomization claim. Add no second scheduler, global worker limit or independent stop/retry policy.

Known route/effort drift emits a durable scoped observation before the existing stop/finalization handling. Restart recovery retains frozen matrix membership, request evidence and expected trials; it must not rebuild cells from a newly changed registry or catalog. Missing diagnostics after a crash remain an evidence gap. User changes to reusable profiles affect only future previews.

## Measurements, scores and normalized persistence

M05 emits `RouteObserved(RequestRouteObservationV1)` independently of the accounting `InvocationFact` union. For result-backed calls, M02 `VariantEvidenceRecorder.append_route_observation(result_id, evidence, operation_id) -> RouteObservationReceipt` owns the common sanitized raw model/effort/route source fact. Its receipt binds operation/observation/source_fact IDs, result/full trial/invocation/request/attempt scope, evidence digest and publication revision; linked `VariantEvidenceV1.source_fact_ref` derives the variant projection without a competing raw writer or stronger confidence. Retain source disagreement, idempotent receipt replay and an inference-call identity even when usage is unavailable. Planner and diagnostic scopes retain evidence in their existing owner journals with no fake result. Pre-seal receipts drain before finalization; later contradiction follows existing annotation/exclusion and analysis-staleness rules.

M10 retains actual usage, timing and cost once per existing scoped inference call/attempt. Correlate harness, gateway and upstream receipts without summing duplicates; gateway charge including upstream cost and upstream provider cost are alternative cost bases unless a separately evidenced additional fee is explicitly additive. Keep raw amounts/currencies, charge owner, exact cost basis, coverage and price/rate snapshots. Different tokenizers/counter semantics remain declared; gateway metadata does not manufacture token totals or generation timing.

Prices belong to the exact access route/account/model/tier and source date. Never substitute a direct-provider or base-model price for an OpenRouter/LiteLLM charge. Preserve all billable upstream attempts, including responses discarded by the gateway, with scoped correlation IDs; missing retry/charge coverage remains partial or unknown rather than silently dropping incurred cost.

Retries/fallback attempts that actually occurred remain attributable even if comparison matching fails. Protocol conversion/network/gateway latency stays in measured elapsed time; separately exposed generation timing follows the unchanged paired-request policy. Local gateway CPU/memory is disclosed host overhead, not claimed model compute. Judge, planner, decision-observer and diagnostic activity remain separate roles; no route receipt turns auxiliary work into competitor score inputs.

M06 uses existing exact arithmetic, full-trial eligibility, persisted analysis snapshots, metrics, category grades and eight ranking factors. Add comparison classifications `confirmed_same_model_effort`, `unverified_same_model_effort`, `exploratory`, and `mismatch`, independently of coverage `all_registry | subset`. Confirmed matching requires complete relevant request coverage and common controls; user declarations cannot promote unknowns. A comparison can be confirmed but have only partial harness coverage.

Only confirmed-compatible subjects enter a labelled same-model/effort cohort; excluded/unverified/mismatched cells remain visible. Missing required trials/checks/grades still exclude a subject under existing scoring. An explicit exploratory analysis can select uncertain cells with disclosures, never override known model-rejection exclusions. Reference extrema are recomputed for the selected eligible population. No per-harness pooled “model score,” hidden trial cherry-picking, new metric or cross-JudgeGroup average is introduced.

This is a separate **harness** comparison axis: the model/variant is held fixed while harness varies. [Model-variant comparisons](MODEL-VARIANTS.md) instead hold harness/effort constant while quantization or fine-tune varies. Preserve their existing matching tiers independently; a confirmed harness comparison is not a strict quant/fine-tune comparison. A selected population that varies both harness and variant is labelled exploratory/factorial, with both axes visible; it cannot receive a one-axis matched label. The analysis link records `comparison_axis=harness` and its classification independently of the variant tier.

The following relational additions extend [results-v1.sql](sqlite/results-v1.sql) and its canonical codecs. They are mandatory typed analytical fields, not a JSON-only attachment. M02 stores sanitized frozen snapshots; the editable local M04 catalog and credential locators are not a second results authority.

Analyses depend on the exact frozen comparison and selected effective-observation/annotation cutoff; new contradictory evidence advances the relevant `resource_revision` and makes older current analyses stale. Preserve historical results “as recorded.” M17 packages only credential-free profile/binding/capability snapshots and scoped observations through existing evidence pins; import registers queryable provenance without activating endpoints, credentials, inspection or inference.

## APIs, CLI and design-engine handoff

Register M04 `catalog.access_profiles.list/get/save/inspect` and `catalog.access_profiles.capabilities`. Saves accept structured drafts, expected version and local credential references; `inspect` is an explicit cancellable metadata job. Capability output includes every requested harness, independently of availability. Use existing error envelopes, JobRefs and ActionStates. No endpoint or model is invoked by list/get/navigation.

M04 also registers `catalog.existing_agent_profiles.list/get/inspect/register`; inspect accepts an explicitly chosen local source/alias and returns a cancellable JobRef, while register consumes its exact inspection ID/digest, expected profile version, reviewed treatment and private resolution bindings. M07 `configs.existing_agent_select` binds that ref with a tagged target (`competitor` plus ConfigurationId, or `harness_judge` without a competitor ID), expected draft revision and reviewed override-set ref; the existing preview/launch transaction remains authoritative. Planner selection belongs to its existing M16 scope, not this setup-entry command. Typed reasons include `unsupported_dynamic`, `profile_source_ambiguous`, `profile_control_conflict`, `credential_precedence_unverified`, `profile_isolation_unsupported` and `profile_source_changed`. Registering or selecting never executes the alias or starts a probe.

Curated CLI templates are `axbenchmark existing-agents inspect --alias ALIAS_NAME --source SOURCE_FILE`, `axbenchmark existing-agents register --inspection INSPECTION_ID --name PROFILE_NAME` and `axbenchmark configs existing-agent-select DRAFT_ID --configuration CONFIGURATION_ID --profile PROFILE_REF --role competitor --expected-revision N`. Registration defaults to the reviewed existing treatment; explicit clean/override choices require the corresponding structured review. Replace placeholders only with an independently supplied, explicitly selected source; no private example is prefilled. Local source arguments never enter exported YAML. Canonical M07 YAML carries the sanitized profile ref, treatment and override refs; an imported configuration with no locally bound registration remains blocked. UI actions use the same owner APIs and revision checks.

M03 registers `environment.qualify_route` with the explicit consent/budget metadata above and supplies `RouteQualificationOutcomeV1` to M04. Its CLI is `axbenchmark access-profiles qualify PROFILE_REF --harness HARNESS --model-binding REF --effort-contract REF --budget FILE`; it exposes planned external calls and requires the existing explicit diagnostics confirmation. A metadata inspection success never schedules it automatically.

Register M07 `configs.comparison_create`, `configs.comparison_update`, `configs.comparison_preview` and `configs.comparison_export`, operating on existing Setup drafts. Creation returns the draft revision and full matrix; update is revision-checked and atomic; preview returns cells/common controls/coverage/digest and disabled-action reasons. `comparison_export({draft_id, expected_draft_revision, output, overwrite:false})` is a write-class command using the M07 canonical configuration serializer and guarded atomic output writer; it returns path, content digest and matrix readiness without saving over the source configuration or starting a run. Events `catalog.access_profiles.updated`, `catalog.access_profiles.inspection_finished` and `configs.comparison.updated` use existing owner topics and revisioned snapshots/EventCursor semantics.

M14 curated commands: `axbenchmark access-profiles list`, `access-profiles inspect PROFILE_REF`, `compare-harnesses --config CONFIG --model-binding REF --effort-contract REF --access-profile REF --trials N`, with `--harnesses` for an explicit subset and `--mode exploratory` for disclosed uncertainty. `compare-harnesses` creates/previews a setup; the existing `runs.launch` API (CLI `axbenchmark run --config FILE`) performs execution. Explicit `--output FILE` exports the generated draft through the M07 configuration serializer as credential-free runnable YAML, atomically with no overwrite by default; subsequent `axbenchmark run --config FILE --no-tui` revalidates the same matrix and settings. Without an output target, return the draft ID for the existing setup/save flow. Exporting a structurally valid but unready plan preserves its blocked cells and cannot make it launchable. No CLI flag bypasses unsupported execution or silently omits a blocked cell.

The design engine should extend [benchmark design handoff](BENCHMARK-DESIGN-SPEC.md), M04.4, M07.3, M05.7, M06.2 and M13 with these states:

- **API access profiles:** Direct/OpenRouter/LiteLLM selection, explicit chained route, endpoint/protocol, model alias/upstream identity, local credential presence, role scope, inference versus gateway locality, and inspection/capability evidence. Never show secret values in previews.

Source-file inspection is explicit and no navigation invokes the agent.
- **Compare across harnesses:** common exact model and effort selection, trials, all-six matrix, per-cell protocol/mapping/status/reason, strict/exploratory policy and explicit selected coverage. Show unsupported effort choices disabled; no inferred closest effort.
- **Review:** frozen shared controls, unavoidable harness differences, route translation/overhead, unknowns, helper scope, cost/budget assumptions and explicit subset acknowledgement. Preserve editable choices after any stale/blocked response.
- **Live/detail:** requested versus resolved/effective model/effort/route, drift and evidence coverage, helper usage, unsupported versus actual failed/partial states. Do not let raw provider output rebind engine identities.
- **Results/report:** harness as comparison axis; full matrix beside existing quality, cost, time, Gen tok/s, In/Out tok and Files/LOC; confirmed/exploratory/mismatch and N/6 labels; saved analysis refs and filters by exact route, variant, effort and scope. Offline reports inspect retained evidence without probing endpoints.

These are new screen/state requirements, not assertions that current prototype boards already implement them. Design should read this document together with [context design](CONTEXT-DESIGN-HANDOFF.md) where route observations affect context evidence, and the applicable human/domain judge handoffs for independent grading selection.
