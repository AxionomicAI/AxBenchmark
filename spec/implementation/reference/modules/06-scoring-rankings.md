# M06 — Weighting, eligibility, and rankings

Authority: [the product specification](../SPEC.md). This module defines required analysis behavior. Its [Implementation](#implementation) section places that behavior in the headless engine fixed by [the architecture decision](../../../ARCHITECTURE.md); every interface presents the engine's results and never computes scores, eligibility or normalization itself.

The [benchmark statistics contract](../../BENCHMARK-STATISTICS.md) is binding for the five additional ranking factors, exact measurements, compatibility and shared acceptance vectors [R173–R176]. It extends existing [M06.1](../../M06/01-scoring-service.md) and [M06.2](../../M06/02-rankings-screens.md); their node identities and the four ranking kinds below are unchanged. [Decision engines](../../DECISION-ENGINES.md) supplies the shared grading fingerprint, not a dependency for statistical ranking. With no decision engine configured, context decision analysis and the decision-grading option are unavailable; native capture, harness grading and deterministic rankings remain available.

This proposed contract defines application-computed scores and rankings, extending the repository README's separate measured cost/time and quality assessments. Rankings compare priorities across complete harness/model/environment configurations; they do not establish isolated model capability. These are required behaviors, not claims of existing implementation. [R004]

## Inputs, outputs, and boundaries

Analysis consumes matching-template results: stable result identifiers, each result's explicit `TrialRef {run_uid, configuration_id, trial_index}`, frozen trial roster, original and effective execution status with run-invalidation overlay, required-check outcomes, raw rubric grades and validity, judge fingerprint, M10 cost/time and statistical observations/summaries with exact values, availability, coverage, policy, basis and provenance, original weights/directions/metric policies, the optional analysis tariff, and current filters. It produces normalized weights, weighted quality, M10-prepared trial means or pooled values and min–max ranges, ranking eligibility and exclusion explanations, enabled-component reference values, contributions, and deterministic ordered results. Original records and legacy unknown metrics remain separately inspectable. [R096, R097, R098, R099, R100, R124, R131, R173–R176]

[M07](07-run-configuration.md) completes setup before launch: independently select the grading backend and judge configuration under M12; the existing harness/model/effort defaults remain applicable to `harness_review`. Use the template rubric and finish both weight choices, directions and metric comparison policies before execution. [M12](12-quality-judging.md) supplies validated raw grades; [M08](08-verification-evidence.md) supplies required-check outcomes; [M10](10-measurements-cost.md) supplies measurements; [M02](02-retained-results-comparability.md) preserves originals and provenance. M06 computes totals rather than accepting judge-calculated totals as authoritative. The new statistics are scorer inputs only: M12 recursively excludes generation speed, input/cached/output/reasoning usage, measured Files/LOC, weights and rankings from all three grading-backend payloads. [R033, R096, R100]

## Weight operations and validation

Expose two independently editable weight sets in the TUI and YAML/JSON. The six quality-category weights determine the overall application grade. Ranking weights use the stable eight keys `cost`, `time`, `quality`, `generation_rate`, `input_tokens`, `output_tokens`, `file_count`, `loc`; product/profile defaults are `1:1:1:0:0:0:0:0`, preserving equal thirds for cost/time/quality. Files and LOC are independently configurable even when grouped for display. Neither set changes the other's normalization; more tokens/files/lines does not imply better quality. [R092, R093, R094, R173–R176]

Quality defaults follow the template profile: frontend/fullstack uses UX 25%, visual quality 15%, code quality 20%, business rules/specification 25%, robustness 10%, and accessibility 5%. Backend substitutes developer experience, API/interface design, and operability/documentation in the corresponding positions. Mobile, DevOps, agentic software and specification design use their own six ordered categories/defaults in M12's versioned domain contracts. Resolve categories, `business_category` and weights from the approved rubric/version/digest, not a latest-profile lookup; legacy payloads and grade meanings remain fixed. M12 defines these profiles; use the same template profile throughout a comparison. [R033, R093, R095]

Support editing, named preset saving/loading, restoring defaults, and previewing normalized percentages. Every supplied weight must be finite, exact and nonnegative, and each set must have a positive total. Require the complete six-category profile map and normalize all eight ranking values together, separately from quality. `RankingWeightsV2 {schema_version: 2, weights, directions}` requires both maps to contain exactly the eight keys: reject missing/unknown keys, negative/nonfinite/unparsable weights and all-zero sets with field-specific errors. Cost/time directions are fixed `lower`; quality is fixed `higher`. A new factor requires explicit `higher` or `lower` before its weight becomes positive; at zero weight its direction may be null. Reject invalid/fixed-direction changes and missing positive-factor directions; never infer a preference from a metric's name. Zero removes the contribution, not raw grades or measurements. [R095, R145, R173–R176]

Only an explicit valid version-1 legacy three-key ranking map migrates in memory to five zero weights and null new directions, with fixed cost/time/quality directions. Preserve original schema, bytes/digest and supplied exact values; never rewrite sealed originals or accept an incomplete/malformed legacy map. Missing version-2 keys are errors, never migration defaults. M07 launch, presets, CLI/YAML/JSON, API and editors use the same complete version-2 schema.

Freeze original weights, directions and metric comparison policies before execution and retain raw grades separately. Exploring alternatives in results or HTML recomputes totals without judge/model calls, probes, new measurements or overwriting original results. Label alternatives, provide reset to the original analysis, and permit alternative configuration/report export. Restoring product/profile defaults and resetting an alternative to frozen originals are distinct operations. [R096, R145]

The original analysis of a judge group uses one common quality set and ranking plan. After legacy normalization, ranking agreement compares the **effective normalized eight-key weights, enabled new-factor directions and selected metric policies**, not weights alone. Disabled-factor policies impose no data requirements. Equal weights with conflicting enabled directions/policies are not a common original plan: use labelled profile defaults with the five new factors zero, or an explicitly selected common alternative. The existing label "Profile defaults: original weights differ across results" remains for weight differences; direction/policy differences receive the corresponding engine explanation. Quality resolves independently to common originals or the profile default and uses one set for every entry. Each result's exact original sets, directions, policies and schema provenance remain visible and selectable as alternatives. Raw grades and originals never change. [R096, R124, R173–R176]

## Calculations

For valid raw category grades gᵢ on the 1–5 scale and normalized category weights aᵢ, quality Q = Σ(aᵢ × gᵢ). Equivalently, multiply each grade by its original category weight, sum those products, and divide by the original category-weight total. The application performs this weighted mean from retained grades. [R096, R097]

For normalized ranking weights summing to one, `score = 100 × Σ(enabled k) w_k × factor_k`, with `contribution_k = 100 × w_k × factor_k`. Quality remains `Q / 5`; cost/time preserve `minEligibleCost / cost` and `minEligibleTime / time` with the existing verified-zero-cost and guarded-zero-time rules. With all new weights zero this is exactly the original three-component formula and behavior. Contributions are keyed by the enabled components, not a fixed three-row structure. [R098, R099, R173–R176]

For a new factor's complete compatible value `x`, `lower` uses `m / x` for eligible minimum `m > 0`; when `m = 0`, complete proven zero receives factor 1 and positive values 0. `higher` uses `x / M` for eligible maximum `M > 0`; when `M = 0`, all eligible complete zeros receive 1. These rules never apply to cost or time. Skip zero-weight components **before** measurement lookup, compatibility checks, extrema or division.

The ranked `ConfigurationSubject` is exactly `(run_uid, configuration_id)`; `run_label` is display metadata, never a key. Every trial is a separate result. M10 supplies mean cost/time and exact full-roster means of input tokens, output tokens, file counts and LOC, with per-trial values and ranges. Generation rate is M10's **pooled** matched-output numerator divided by summed matching request-generation seconds across every trial, with retained numerator/denominator and per-trial range; M06 never substitutes a mean of rates, wall time or its own measurement aggregation. M06 adds mean/min–max quality. A configuration enters a ranking only when every frozen trial is eligible for that ranking; one trial equals its trial value. Missing trials exclude the subject, and filters or judge selection cannot shrink the roster. Missing selected-judge reviews remain ungraded. All summaries retain full TrialRefs, policies, coverage and unknown/partial states. [R077, R100, R154, R173–R176]

Select an explicit compatible metric policy/basis cohort before forming the eligible population; then compute **every enabled reference from that same eligible population** after all gates, filters and judge grouping. Incompatible candidates without a common selected policy make the affected ranking uncomputable, never an implicitly favorable subset. Recompute references when filters, alternatives or overlays change. Exact rational arithmetic covers normalization, quality, references, factors, contributions, scores and ordering; round only for display. A displayed tie is not an exact tie. Exact ties retain the stable result-identifier key, keeping separate runs distinct. [R099, R124, R131, R173–R176]

## Eligibility and exceptional data

Default shortlists require completed execution, verified required checks, valid required grades, and a raw business rules/specification grade of at least 4/5. Failed or unverified required checks cannot satisfy verification. A high weighted quality score cannot bypass these gates. [R100]

Exclude an entry missing a positively weighted measurement from the affected ranking and explain why; never redistribute its weights across available components. A partial measurement counts as missing for any ranking in which it carries positive weight: partial cost excludes the entry from the lowest-cost ranking and from combined rankings with a cost weight above zero, and partial elapsed time likewise for time. The entry stays in tables with its partial value, its coverage and an explanation such as "cost covers 6 of 7 tasks". A zero-weight component contributes nothing and requires no measurement for that component. This does not waive the separate required-grade and business-grade eligibility gates. Keep failed, incomplete, and excluded entries in full tables with their status visible. Direct lowest-cost, shortest-time, and highest-quality shortlists apply the eligibility and measurement requirements relevant to their ranking. [R100]

Positively weighted new factors apply only to `COMBINED`; they never impose data gates on `LOWEST_COST`, `SHORTEST_TIME` or `HIGHEST_QUALITY`. Require complete known compatible data in every expected trial and its full-roster summary. Exclusions carry metric key, failing full TrialRefs and `metric_unknown`, `metric_partial`, `metric_basis_incompatible`, `metric_policy_incompatible` or `metric_scope_incompatible`; retain observed values and never renormalize per entry. Compatibility matches normalized token semantics, timing basis and artifact scope/counting policy as applicable. Native model/tokenizer IDs remain interpretation metadata, not equality gates between competitors. Legacy absent metrics stay unknown and affect eligibility only when enabled. A known zero rate requires complete output evidence and a positive matching duration; missing or nonpositive matching duration leaves throughput unknown/partial, never a fabricated zero.

The cost that counts for rankings is [M10](10-measurements-cost.md)'s: a reported cost; a verified $0, which holds only when the provider or harness reports $0, usage coverage is complete for every task and the account's billing kind is known and not a subscription (an unknown billing kind never yields a verified $0); an API-equivalent estimate from the price table recorded at launch, labelled as an estimate with its price source and date; or, in sequential runs only, for a configuration on a local endpoint with no API cost, the energy-cost estimate (measured kWh in that configuration's execution windows × tariff), labelled "energy estimate" with its measurement scope (for example GPU + CPU package, not whole-system). A subscription or a missing price is never $0. In parallel runs shared energy is never divided, so such a configuration's cost stays unknown; without a tariff or an energy measurement it is unknown too. A tariff entered in Results as an analysis setting recalculates the energy estimate for the analysis, labelled as alternative, without changing the recorded one. [R101, R114, R155]

**New edge-case policy (F08), from SPEC §6:** retain any numeric zero lacking M10's verified-zero basis, including zero API and energy estimates, with its original value and basis. Exclude the trial and its entire subject from lowest-cost rankings and combined rankings with positive cost weight using `cost_zero_unverified`; never divide by it or promote it to verified zero. Cost weight zero removes this measurement gate only. Unknown billing retains any valid positive reported/estimated cost, with its limitation and billing label visible. [R080, R100, R101]

Rankings compute in USD. Costs display in the compared runs' frozen display currency, or in USD with a note saying so when the compared runs froze different display currencies; there is no analysis-time currency choice. [R081]

When a verified eligible minimum cost is zero, every verified zero-cost entry receives its full cost contribution, 100 × w꜀; positive-cost entries receive zero cost contribution. Unknown cost never becomes zero. If fewer than five qualify, show only that number; if none qualify or no ranking can be computed, explain the cause. The source gives no corresponding zero-elapsed-time convention; treat that as an unresolved calculation case rather than inventing a ratio or copying the cost exception. [R101]

## Comparison and presentation contract

Within a matching template, display and filter by originating machine, harness/model/effort, environment policy, concurrency, and judge configuration. Machine differences are intentional inputs, not hash mismatches. Apply the common selected plan while retaining originals. `JudgeGroup` follows the [shared grading fingerprint](../../DECISION-ENGINES.md#evidence-bound-decision-grading): backend kind, decision profile/version/digest, requested/resolved model, runtime/quantization where relevant, rubric/pack/mapping/evidence-policy digests and acceptance policy. Harness, decision and human grades never pool merely because labels/models/templates match; Human uses its frozen self-declared reviewer/form-policy fingerprint and no model fields. Expose local/imported provenance, cost bases (reported, verified $0, API-equivalent estimate, energy estimate with its scope), and measurement limitations; differing cost bases alone are not an automatic exclusion. Every read applies M02's run invalidation overlay: an invalidation excludes every trial of that UID, including sealed results/reviews, without rewriting facts. M02 inspection remains available; an open breakdown refreshes to `scoring.not_comparable`, never a stale score. [R067, R124]

[M13](13-standalone-html-report.md) uses the README presentation as its starting point and identifies the template and full SHA-256 in every report. Measured tables default to highest known cost first, unknowns last; quality tables default to descending unrounded quality within judge groups. Support sorting, machine/configuration/judge filtering, and task-detail/evidence inspection. [M15](15-terminal-interface.md) and M13 consume the same scoring contracts, served by the engine. [R131]

Human grading follows the same exact six-grade/Q/business-category and full-trial rules. Only committed server-validated GRADED reviews supply quality; awaiting/draft/submitting/ungraded/skipped/cancelled states remain explicit missing/invalid selected-review exclusions, even at zero quality weight. M06.1 and M06.2 test identical raw-grade parity, distinct reviewers/groups, one pending trial excluding its whole subject, and additional review selection without changing originals. Measurements remain inspectable and no analysis operation creates a form or model call. **R189**

## Implementation

Implementation decisions under [the architecture decision](../../../ARCHITECTURE.md) place the specification and binding statistics rules above in the existing children. Version-2 omissions are validation errors; zero elapsed time retains its guarded unresolved state. Existing three-component prototypes represent the default plan only and do not limit the expanded runtime contract.

### 1. Engine component

Package `axbenchmark.engine.scoring`. Domain rules and `analyse_population` compute purely over prepared inputs. Application/query wrappers read retained data through ports and retain/reuse derived analyses through M02 before returning completed scores; M06 owns no result database or independent mutable score store, publishes no events and starts no processes. Original weights are frozen by [M07](07-run-configuration.md) and retained by [M02](02-retained-results-comparability.md); named presets are persisted by M07 ([M02](02-retained-results-comparability.md) records "scoring presets persisted in YAML by M07"). Direct file output is limited to an exported alternative weight configuration at a path the user chooses; analysis retention uses the M02 SQLite sink and never mutates original facts.

**Domain** (`engine/scoring/domain/`, no I/O). All arithmetic uses `fractions.Fraction`, so normalization, Q, references, factors, contributions, scores and comparisons are exact; API exact rational strings preserve every input/derived value used in ordering or offline recomputation; approximate floats are presentation conveniences only. Round only for display. All measurement aggregation and currency arithmetic remain M10-owned. [R099, R131]

`Population` also pins shared `VariantFilterV1`/`VariantComparisonSelectionV1`, per-subject descriptor/effective/annotation projections, every expected trial's controls and versioned comparison policy. `VariantComparisonV1` carries status, selected/candidate signatures, field-level confounds/exclusions and affected full TrialRefs. Unknown fingerprint/control values cannot equal each other. Both query-backed and prepared-input paths apply these same pure classifications; no new score component/formula is introduced. **R190**

`RankingService.analyse_population(population, group, selection)` is the authoritative prepared-input entry. Validate binding/count/map consistency, group and versioned weights/directions/policies, then delegate to the existing pure `analyse`/`resolve_original` rules; no second scorer, fresh query, profile lookup, measurement aggregation, conversion or tariff application occurs. Missing expected trials remain valid population data and yield all-trial exclusions. Reject an inconsistent binding with `scoring.inconsistent_population` or supplied non-comparable/invalidated scope with `scoring.not_comparable`; never silently drop a supplied invalidated run. Eligible references, exclusion explanations and all trial gates use only this pin. A later invalidation cannot be discovered without a new read: API refresh rebuilds the population, while M13 rechecks its captured versions at guarded artifact publication and rejects a changed/invalidated scope.

### 2. API surface (`scoring.*`)

No `scoring.*` analysis request accepts display currency, rates or an ambiguous `run_id`. ## Durable analysis identity — R191

The [SQLite results contract](../../RESULTS-DATABASE.md) binds every retained raw/derived score to normalized storage. M06 remains the sole eligibility/scoring authority. Pure prepared-population calculations stay pure; query and report wrappers retain/reuse their output through M02 before reporting completed engine scores, adding analysis identity/input digest to ranking/breakdown DTOs.
