# M07 — Run configuration and launch validation

Status: proposed requirements. This module defines reusable setup and the immutable settings handed to execution; it does not describe implemented functionality. [SPEC.md](../SPEC.md) remains authoritative.

## Purpose and scope

A template defines the specification, ordered tasks, starting files, acceptance checks, execution protocol, and grading rubric. A run configuration selects harnesses, providers, models, efforts, environment settings, judge, and scoring weights for that definition. A result records one configuration's outcome on one machine against the exact template revision. Keep these concepts distinct so users can vary execution choices without redefining benchmark work. **[R017]**

Persist reusable configurations per template revision and scoring presets in YAML. Save harness/model/effort choices for each benchmark, with every configuration pinning its template SHA-256. Users may add or edit configurations for a future run without changing that hash or overwriting previous results. ZIP exchange carries templates and results through [M17](17-zip-exchange.md). Imported templates can use destination-machine harnesses; originating executable paths, credentials, and hardware are not template prerequisites. **[R009, R019, R066]**

The library's existing seven-task inventory benchmark is the default and runs without generating tasks. Templates created, duplicated, revised, or imported through the library and planning modules also support their own saved configurations. Selecting an approved revision must preserve its approved task suite. **[R136, R037]**

## Configuration behavior

Load the selected revision's saved configurations or let users select harness/provider/model/effort combinations. Allow multiple entries for the same harness so distinct configurations can be compared. Default environment policy to clean settings and offer current settings. Apply the isolation semantics and limitations of [M05](05-harness-execution-isolation.md); do not silently change an unavailable clean policy to current settings. **[R032]**

Judge selection is independent of competitor and context-monitor selection. `harness_review` remains the default: preselect a valid saved judge harness/model/effort selection first, otherwise the planner configuration if planning was used, otherwise the first selected usable configuration. Resolve and validate the candidate using current readiness and capability information; an unusable candidate must not become an executable choice by assumption. An explicit `decision_rubric` selection uses its own ready profile; `human_review` uses the frozen local reviewer/form-policy and host/renderer readiness. Neither silently falls back to harness review. Explain any unresolved selection before launch. The user can change the judge independently. Apply the template's rubric and one grading profile to every configuration in the comparison. Defaults are selection conveniences, never model-quality recommendations. **[R033, R037]**

Provide editable quality-category and eight-factor ranking weights, reusable presets, and restoration of defaults. [M06](06-scoring-rankings.md) owns validation, normalization and previews: `RankingWeightsV2 {schema_version: 2, weights, directions}` has exactly `cost`, `time`, `quality`, `generation_rate`, `input_tokens`, `output_tokens`, `file_count`, `loc` in both maps. Defaults retain equal cost/time/quality and five zero weights; cost/time are `lower`, quality is `higher`, and each positive new factor requires an explicit `higher`/`lower` direction and compatible metric policy. No metric implies a quality preference. The independent quality categories/defaults remain [M12](12-quality-judging.md)'s. Resolve and freeze both sets, directions and metric policies before launch so later preset edits cannot alter them. See [benchmark statistics](../../BENCHMARK-STATISTICS.md). **[R033, R066, R145]**

Without a configured compatible READY decision profile, new context-window analysis/reclassification and the decision-model grading option are disabled. Native capture/basic usage, harness grading, deterministic rankings and offline saved analyses/reviews remain available. Each enabled operation requires an explicitly selected ready profile for its own role; selecting a grading profile never enables context analysis. Disabled controls show the engine's reason and a **Configure decision engine** action; profile editing/testing stays accessible. API/CLI enforce the same gate before dispatch. An unavailable optional observer does not invalidate competitors; an explicitly selected unusable decision grader blocks launch.

Execution settings include the number of trials per configuration (default 1; any positive whole number is accepted, with no upper limit, and anything else is rejected), the hardware sampling interval (0.5–10 s, default 1 s, validated by [M18](18-hardware-monitoring.md)), the display currency (default USD) and an optional electricity tariff per kWh with its currency (both validated by [M10](10-measurements-cost.md)). All of them are set in Setup or in the configuration YAML before launch and are frozen with the run; none of them is part of the template identity. Later analysis may choose alternative tariffs and weights; it cannot choose another display currency or refresh the run's rates. M10 uses each run's frozen rates and displays mixed-currency comparisons in USD with an explicit notice. **[R066, R081, R106, R114, R154; F07]**

The configuration holds no exchange rates. At launch, the catalog ([M04](04-model-catalog.md)) supplies stored rates for every competitor/judge price currency, display currency and tariff currency. Freeze them beside the prices, preserving source URL, source date, retrieval date, supplied/unknown state and labels. `per_usd` means currency units per 1 USD (COP `4000`), never its reciprocal. A missing rate remains missing and any conversion requiring it is unknown; no rate is guessed, and the historical README exchange rate is never used. Rates are never collected during review, launch or a run. **[R081, R156]**

Each selection's billing kind (`api`, `subscription`, `local`, `unknown`) is taken from M04 at launch with its source, observation origin/date, declaration flag and engine label. Preserve an explicit unknown declaration as well as a known declaration; both remain labelled "declared by user" wherever the launch shows a cost basis. Unknown billing is frozen as unknown and never supports a verified $0 ([M10](10-measurements-cost.md)); positive amounts retain the limitation. **[R080, R157]**

Setup and review always show configurations × trials × tasks task runs and the number of judge sessions ([M12](12-quality-judging.md)). When a launch requests more than 5 trials and at least one configuration has remote, mixed or unknown inference locality, launch validation returns a non-blocking trial budget warning with those totals. The launch review asks for confirmation in a dialog stating that the extra trials will consume budget and subscription usage. The warning is not raised when every configuration has evidenced local inference, regardless of gateway location, regardless of the independent judge's endpoint. An unattended launch prints the warning and continues; it never prompts. **[R077, R158]**

Before execution, show the complete setup: template identity, all competitor entries and their providers/models/efforts, environment policies, independent context and grading role selections with frozen profile evidence, grading profile, both weight sets with directions/metric policies, and execution settings supplied by the scheduling and isolation modules. Show relevant readiness and isolation limitations. The displayed setup and resolved launch settings must agree. **[R032, R033, R037]**

## Conceptual data and operations

Maintain three distinct records: reusable revision-scoped configuration choices, reusable scoring presets, and the resolved launch configuration. The resolved configuration includes all selections actually authorized for that launch and its original weights. Preserve the requested choices and capability evidence under the [M04 catalog contract](04-model-catalog.md); this module introduces no model identifiers, effort values, or catalog schema. **[R017, R066]**

Loading, adding, editing, and saving operate on reusable choices. Unsaved setup edits are kept as a draft on disk under `~/.axbenchmark/drafts/`, so a draft survives a closed interface and an engine exit until it is saved or discarded. Resolving and validating operate on a prospective launch. Freezing produces the immutable execution input; later configuration edits affect future runs only. Capture the pinned hash, resolved configuration, originating machine identity/details, and catalog metadata used at launch, including a snapshot of the provider prices used for each selection with their source and retrieval date, each selection's billing kind with its source, and the snapshot of exchange rates with their source and retrieval date, for [M02](02-retained-results-comparability.md) to retain with each result. Redact credentials from exported settings, logs, and reports, including diagnostic descriptions derived from configuration. **[R019, R066, R067, R080]**

## Validation, failures, and invariants

Before execution, ask [M01](01-template-library-identity.md) to recompute the selected template's SHA-256 and verify the configuration's pin. Its immutable definition includes the approved specification, prompts, checks, rubric, execution protocol, and starting snapshot. A mismatched pin cannot launch as that claimed revision. Bind each result to the verified identity, then separately freeze the resolved configuration and original weights before execution begins. **[R067]**

All competitors use the same approved suite and grading profile. Configuration changes cannot alter those inputs. During execution, detected mutation of template inputs invalidates the result's claim to that template and halts the whole run ([M11](11-run-orchestration.md)); never silently relabel the result with a newly computed identity. The execution lifecycle must preserve this invalidation and the original launch record. **[R037, R067]**

Use M03 readiness, M04 compatibility, M05 environment controls, M12 judge requirements, and M06 weight validation when determining launch readiness. Explain invalid or incomplete settings at setup; do not claim compatibility from a model name or invent effort choices. Unattended launch uses the same contracts through M14 without waiting for interactive configuration. **[R032, R033, R066]**

The application computes totals from separately retained raw judge grades. Alternative weights in results or HTML recalculate totals without judge calls or overwriting original results. Label alternatives, allow reset to original weights, and support exporting the alternative configuration/report through M06, M15, and M13. Original weights, grades, and outcomes survive every analysis change. **[R096, R145]**

Human setup/review tests restore saved explicit Human across all six families, independent of competitor and context roles, with no invented model/account/effort/confidence requirement. Freeze reviewer/form-policy versions/digests and evidence/form bounds in preview/launch/group identity; profile edits stale a preview but cannot rewrite a launch. SetupView/LaunchPreview/TrialBudgetWarning/LaunchTotalsDTO expose human_cases and logical assessments separately from machine counts. Review discloses the single post-seal anonymous queue, one case per expected trial, human-input completion barrier and no human wait in benchmark timing. **R189**

## Acceptance criteria

- Save distinct YAML configurations for two revisions; changing one leaves both template hashes and historical results intact. Repeat with an imported revision using local harnesses. **[R009, R019, R066, R136]**
- Configure multiple entries for one harness, switch clean/current settings, and verify the complete setup matches the resolved launch. **[R017, R032]**
- Set trials, sampling interval, display currency and tariff in Setup and in YAML: invalid values are rejected with the owner's explanation and never replaced; valid values appear in review and in the frozen record, and the template hash is unchanged. A trial count of 50 is accepted. **[R066, R077, R106, R114]**
- Launch with 6 trials and one cloud configuration: review shows the trial budget warning with task-run and judge-session totals and the TUI asks for confirmation before launching; `run --no-tui` prints the warning and continues. With 6 trials and only evidenced local inference configurations, or with 5 trials, no warning is raised. **[R077, R158]**
- Launch with prices in USD and EUR and display currency COP: the frozen rate snapshot holds EUR and COP with source and date (USD needs none), and a user-supplied rate is labelled as such. Without a catalog rate for EUR, the snapshot records EUR as missing and the launch proceeds. Refreshing rates after launch leaves the frozen snapshot unchanged. **[R081, R156]**
- Declare an account's billing kind in the catalog: review shows it labelled "declared by user" and the frozen record keeps the declared kind and its source; an account with no reading and no declaration is frozen as `unknown`. **[R080, R157]**
- Edit a setup, close the interface and restart the engine: the draft reopens with its unsaved edits until it is saved or discarded. **[R019]**
- Exercise each judge-preselection branch, independent judge editing, common suite/profile, and completed weight selection; defaults make no quality claim. **[R033, R037]**
- Verify launch records preserve machine/catalog metadata, the price snapshot with source and date, billing kinds with their source and the rate snapshot, exclude credentials from exports/logs/reports, and freeze configuration and original weights before execution. A mismatched or mutated template cannot retain a verified matching claim. **[R066, R067, R080]**
- Save, reload, validate, reset, and export both weight sets; alternative calculations preserve raw grades and original results and require no judge calls. **[R096, R145]**

## Implementation

This section applies [the architecture decision](../../../ARCHITECTURE.md) to run configuration. Everything below is an implementation decision; the product behavior above stays authoritative. All validation, judge preselection, preset resolution and freezing run in the engine; Setup, review and the CLI only present what the `configs.*` methods return.

Delivery is split into [M07.1 configuration-drafts](../../M07/01-configuration-drafts.md), [M07.2 launch-preparation](../../M07/02-launch-preparation.md) and [M07.3 setup-review-screens](../../M07/03-setup-review-screens.md). Their foundation gates separate completed implementation prerequisites from published contracts used as fakes; parent completion also requires the real integration gates. **F15**

### Binding decision-profile and statistics extension

[Decision engines](../../DECISION-ENGINES.md), [context monitoring](../../CONTEXT-MONITORING.md) and [benchmark statistics](../../BENCHMARK-STATISTICS.md) extend the existing children: **M07.1** owns draft/config/preset schemas and role validation; **M07.2** owns review and immutable role/weight freezing; **M07.3** owns setup, the decision-profile editor and disabled-state navigation. No new M07 child is introduced. M12.4 owns profile storage, CRUD/testing, capabilities and transport; M07 consumes its published APIs.

`context_monitoring {capture_enabled: true, enabled: false, decision_profile_ref?: {id, version, digest}, question_pack_ref, acceptance_policy, budget, resource_policy}` keeps native capture separate from classification. `grading_selection` uses M12's canonical `GradingBackend`/`JudgeSelection` union: `harness_review {existing judge config}`, `decision_rubric {profile_ref, question_pack_ref, acceptance_policy, evidence_policy}` or `human_review {reviewer_ref, form_policy_ref}`. The two role references may differ. Empty new drafts keep analysis disabled and use existing harness judge defaults. Archived configurations and raw evidence keep their original bytes/provenance; this fresh implementation adds no old-install migration, automatic reclassification or backfill. Import/viewing triggers no inference.

A selected M12.4 `DecisionEngineProfile` carries `systemone/1`, endpoint/dialect, auth mode/credential reference, requested/resolved model and exposed artifact digest, immutable profile version/digest, runtime/server version, capabilities, timeouts/budgets, locality evidence (`local | remote | unknown`, declared/verified) and resource policy. Use the shared native System One API for remote TypeSafe and compatible local Ollama; generic chat compatibility, including LM Studio chat compatibility, proves nothing here. Native System One has no harness effort or generation controls. Never expose credential values.

Profile save creates a new immutable version. Testing records a separate readiness/capability observation bound to the exact profile version/digest, or saves a new profile version when capability declarations change; it never mutates immutable capabilities in place. M07.2 freezes the full profile snapshot and exact tested observation/capability evidence, requested/resolved model identity, budget/resource policy and role-specific pack/acceptance/evidence policy with the launch digest. Later profile edits/tests cannot alter an active run or retained review; launch revalidation detects changed readiness before dispatch.

Local or unknown-routing analysis/grading defaults to deferred execution until no managed competitor measured window is active across any run; M11/M12.4 own atomic resource admission. Explicit `live_local_overlap` is frozen and disclosed. Profile tests default to metadata/connectivity inspection with zero inference; an explicit inference smoke test states cost/resource mode before starting and uses a bounded cancellable job, budget and resource lease. Transport cancellation alone cannot promise server termination or a clean release.

Valid legacy three-key ranking weights migrate in memory to complete schema-2 maps with five zero weights and null new directions, retaining original schema/bytes/digest. Missing schema-2 keys remain errors. M07.1 presets/exports and M07.2 frozen originals retain exact supplied values, all eight directions and selected metric policies; M06 alone validates and computes preview percentages, eligibility and scores. UI code does no scoring math.

M07.3 owns `tui/screens/decision_engines.py`, its viewmodel/style/tests and existing feature-route registration. `decisions.profiles.list/get/save/test` and `decisions.capabilities` serve the editor; role choice remains its existing context setter for context monitoring and `configs.set_grading_selection` for tagged grading (configs.set_judge remains harness-only). `can_enable_context_analysis` and `can_choose_decision_grading` require compatible READY native System One evidence and explicit independent role selection. Missing setup returns a typed reason/setup route; ordinary OpenRouter/LiteLLM profiles never enable these flags. Review discloses sanitized admitted content, destination, identity, confidence/budget and local deferred/overlap policy. Human availability uses its host/renderer; optional observer unavailability never blocks competitors, basic metrics or eligible harness/human grading. **R165, R167, R168, R172**

### 1. Engine component

Package `axbenchmark.engine.configs`, API namespace `configs.*`. The module owns saved configurations, scoring presets, persisted setup drafts and the frozen launch records. It starts no processes; the launch itself is M11's `runs.launch` job, which calls this module's `LaunchPreparation` Protocol for resolution and the two freeze steps.

Three record kinds stay separate types, files and digests, as required above: the reusable `RunConfiguration`, the reusable `ScoringPreset`, and the `FrozenLaunch`. A fourth, the `Draft`, is the engine-held working copy that Setup edits; it is never a launch input until resolved. **[R017, R066]**

**Domain** (`engine/configs/domain/`, frozen dataclasses, no I/O):

Existing harness catalog/effort/readiness and `SelectionEvidence` references for a judge below apply to `harness_review`; `decision_rubric` obtains its corresponding identity/capability/readiness and pricing provenance through M12.4's published profile facts. No synthetic harness selection or effort is created for HTTP decisions. Logical assessment totals preserve configurations × trials for every branch. Human requires no machine pricing/capability evidence and has human_cases equal to that total, with zero judge_sessions and decision_call_bound.

### 4. Screens

Every screen below is a view over `SetupView`, `JudgeCandidates`, `LaunchPreview`, `LaunchRecordDTO` or M12.4 decision-profile DTOs. It renders issues, limitations, readiness text and capability flags exactly as returned, displays typed errors verbatim, and never decides validity, preselection, normalization or what will be frozen.

**Decision-engine design handoff (contract-only):** M07.3 extends its existing ownership with `DecisionEnginesScreen` and profile editor in proposed `axbenchmark/tui/screens/decision_engines.py`, matching `tui/viewmodels/decision_engines.py`, styles and screen/view-model tests, plus `SetupScreen` integration. M15 exposes one injected screen factory from the global command palette, Setup and disabled context/grading controls. Profile management requires no enabled analysis feature or active run. Existing rendered wireframes and the [ownership ledger](../design/wireframe-tui/ownership-ledger.md) remain unchanged; these are required new states, not implemented artboards. Design work reads this section, the three [binding extension contracts](#binding-decision-profile-and-statistics-extension), [M12.4](../../M12/04-decision-engines-runtime.md) and the ledger.

The flow is **list → create/edit → save new version → metadata test → choose explicitly for a role → review frozen roles**. Calls are canonical `decisions.profiles.list/get/save/test` and `decisions.capabilities` from M12.4; save/test errors and cancellable jobs retain their owner semantics. Presets select TypeSafe remote or compatible Ollama local dialect/destination; the editor shows endpoint, auth reference, model identity, capability/limit evidence, timeout/budget and resource policy. Test mode is visible before activation; inference smoke checks require explicit selection and show budget/cancellation state. No native System One effort or generation widgets appear.

Widget-ready engine states are `no_engine`, `configured_not_ready`, `ready_text_only`, `ready_vision`, `local_model_missing`, `auth_unsupported`, with returned reasons and loading/error/test-progress variants. Only compatible READY profiles enable role actions; each operation still needs its selected ready profile. A text profile may enable context classification but cannot satisfy web grading's vision requirement. Disabled analysis/grading controls retain the **Configure decision engine** CTA; recheck refreshes immutable-profile-bound observations without changing another role.

Setup and launch review show separate monitoring and grading cards, including disabled reasons, exact profile/version/digest, model/server/device identity where exposed, metadata/probe age, capability evidence, admitted content, acceptance/budget and deferred/overlap policy. Review confirms both frozen roles before launch and invalidates its digest when a selected version or relevant readiness observation changes. Existing JudgeScreen controls edit only `harness_review`; choosing a decision grader uses the shared profile route. Weight controls delegate all eight factors, required directions, policy selection and score previews to M06's WeightsScreen.

## Frozen model-variant selection

[Model variants](../../MODEL-VARIANTS.md) adds optional `model_variant_ref: ModelVariantRefV1` to competitor entries; genuine absence in a new unclassified selection or archived configuration means Unknown metadata, not a fabricated base model or no-quantization claim. Keep the native `model` selector, CatalogContext/EntryKey, variant ID, immutable descriptor digest, execution fingerprint and full configuration fingerprint distinct. A metadata reference cannot make an unserved model available or authorize downloads/loading. Existing grading selections, including human_review, remain intact.

M07.1–2 resolve through M04, expose creator-role/date-kind/source/uncertainty detail in Setup, and freeze the requested descriptor, artifact-manifest/proof coverage, creator/date/lineage snapshots and comparison controls with each launch. Material changed evidence makes an approved preview stale under existing rules. Known contradictory effective content blocks dispatch; unverified but otherwise usable selections remain visibly unverified. Never inherit a base model's prices or billing into its derivative. Variant selection belongs to run configuration and does not change the benchmark definition SHA. Changing a saved entry cannot retarget historical launch bindings or silently reclassify scores.
