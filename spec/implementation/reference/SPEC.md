# AxBenchmark — General Product Specification

Status: proposed product requirements. This document describes the application to build; it does not claim that the functionality is already implemented.

## 1. Purpose and scope

AxBenchmark is a Python terminal application for comparing coding-agent harnesses on representative one-shot and multi-step software work. Users choose a reusable benchmark template or create one from an exact prompt or ordered specification files, with optional idea-to-plan generation for multi-step work, run selected harness/model configurations, collect measurements, obtain independent automated or human quality reviews, and produce an interactive report. Results from other machines can join a comparison when their benchmark template's SHA-256 matches.

The intended users are developers and teams choosing coding agents for their everyday work. This specification gives future implementers the agreed product behavior, defaults, and acceptance criteria. Beyond separating a headless engine from its interfaces, it does not prescribe the internal architecture; [modules/ARCHITECTURE.md](../../ARCHITECTURE.md) records that implementation decision.

The product extends the methodology and presentation in the archived benchmark's [README](../../../legacy/README.md): measured cost and time, a separate quality assessment, and rankings that help users compare different priorities. Results describe complete harness/model/environment configurations, not isolated model capability.

### Initial scope

- Support macOS and Linux.
- Detect Claude Code, Codex, Grok CLI, Pi, Cursor CLI, and OpenCode installed on the local machine, in that display order.
- Support frontend, backend, fullstack, mobile, DevOps, agentic-software and specification-design tasks in either benchmark mode, building from an empty target folder or modifying an immutable capture of a populated folder's current contents; Git is optional for authoring/capture and required for competitor execution.
- Provide a benchmark library with the existing inventory application as the default template, plus user-created and imported templates.
- Save harness/model/effort selections per benchmark and exchange templates and results between machines using ZIP packages.
- Allow configured cloud providers and local model endpoints through supported harnesses.
- Use a TUI as the primary interface. Tmux is not required or used by the product.
- Keep all benchmark logic and state in a headless engine. The TUI and the CLI are interchangeable clients of it, and a later MCP server can be another; no behavior depends on which interface started it or whether one is attached.
- Run every planner, competitor, and automated judge invocation in headless mode; human reviews use the engine-backed browser form.
- Collect local CPU/GPU measurements when compatible tools, hardware, and permissions are available.
- Export a standalone HTML report that opens by double-clicking the file.

Remote machine orchestration, hardware provisioning, and native Windows support are outside the initial scope. Running the application independently on another machine and exchanging ZIP packages is supported. Historical benchmark applications, results, and reviews remain preserved.

The dependency-free requirement applies to the exported report. The Python application may use dependencies, and generated projects may use the technologies agreed in their task specification.

## 2. Benchmark library and user workflow

### Templates and run configurations

A **benchmark template** is the reusable definition of the work: benchmark type, any approved common specification context, ordered primary task files, starting files, acceptance checks, execution protocol, and grading rubric. Its logical specification view contains common context and all ordered primary files exactly once; a singular global specification is not required for new definitions. A **run configuration** selects the harnesses, providers, models, efforts, environment settings, judge, and scoring weights to use with that template. A **result** is the recorded outcome of one configuration trial on one machine, linked to the exact template revision it ran.

Every launch has an immutable globally unique UUID (`RunUid`), preserved through import and re-export, and a separate human-readable date/suffix label (`RunLabel`). Group configurations and trials by the run UID, never by the label or configuration identifier alone. Different machines may use the same label; views and commands must distinguish those runs using their origins and UIDs.

Show built-in, user-created, and imported templates in the library, including their name, description, benchmark type, project type, derived target mode, ordered primary files, task count, baseline provenance, template revision/SHA-256, saved configurations, and available results. Users can select an existing template, create a new one, duplicate/edit a template into a new revision, or import/export it. Running an approved template does not invoke the planner or regenerate its tasks. A duplicate or revision whose SHA-256 equals an existing revision cannot be approved as a new revision.

Save run configurations per benchmark template revision, not as one global harness selection. Users can add or change configurations before a new run without changing the template or overwriting previous results. Imported templates remain usable with the harnesses available on the destination machine; another machine's executable paths, credentials, and hardware are not template requirements.

### Benchmark types and target folders

Treat `benchmark_type` (`one_shot` or `multi_step`), `project_type` (`frontend`, `backend`, `fullstack`, `mobile`, `devops`, `agentic`, or `specification`), and derived `target_mode` (`from_scratch` or `modify`) as independent dimensions: both benchmark types support either target mode for every applicable project type. Follow the binding [benchmark modes and current-folder baseline contract](../BENCHMARK-MODES.md). One shot preserves the user's exact UTF-8 prompt bytes as one frozen task, `T1`, and starts one fresh logical competitor session per configuration trial. Normal model requests, tools and transport retries may occur within that task; one shot does not mean one model API call. Reject invalid UTF-8 and empty/whitespace-only input without rewriting it. Never force a planner, paraphrase or split the prompt, duplicate it as global specification, or add an automatic QA/fix task. Approved execution-protocol instructions, including required task commits, accompany the exact prompt without rewriting its bytes or expanding its authored deliverables. Acceptance checks, final regression and independent grading remain separate engine phases and never add competitor repair work.

Manual multi-step authoring accepts at least two supplied UTF-8 specification files, exactly one primary file per ordered task, preserving each file's bytes and the user's explicitly reviewed order. Missing, duplicate, unreadable, invalid or empty inputs fail validation; filesystem order cannot choose task order. Hash that order and those bytes. Each step starts a fresh process/conversation while its trial's workspace carries state forward. Supply approved common context and the introduced specification prefix through the current step without injecting future step files; pre-existing baseline or generated workspace information remains honestly visible. An optional idea-to-planner route creates a reviewed multi-step template, defaulting to seven tasks including its authored final verification/fixes task. Manual authoring has no seven-task requirement and never requires planning; neither reuse nor import triggers planning.

Inspect the user-selected readable target directory's current working bytes, including eligible tracked, modified, staged and untracked files, binary files and non-Git folders; the working file wins over the index or `HEAD`, and a selected subdirectory remains the capture root. Determine emptiness before exclusions: ignore only the versioned VCS/OS administrative-entry policy and empty directories; any other content, even unreadable, unsupported or later excluded, establishes `modify`. A folder without meaningful project content derives `from_scratch`; inspection failures and nonempty excluded-only folders fail actionably instead of becoming empty baselines. Review admitted files, exact exclusions and reasons before capture. Never follow links or broaden the root; apply portable path validation and preserve semantic executable flags. Compare source inventories, copied bytes/modes and a post-copy inventory, with bounded retry or an explicit source-changed error; this is consistency evidence, not an atomic filesystem snapshot claim. Reject stale capture/approval previews. Publish only a complete immutable capture and give every configuration/trial an isolated writable copy. Leave the original directory, Git state and user edits untouched throughout inspection, capture and execution. Later runs, reuse and ZIP imports use packaged source bytes even when the original changes or disappears; an explicitly requested refresh requires a newly reviewed draft/revision.

New authoring uses strict `axbenchmark-definition/2`: record benchmark type, role-bearing shared/primary file references, explicit ordered tasks and empty/folder baseline metadata, while retaining the required checks, protocol, services, dependencies and rubric fields and their completeness validators even when no planner ran. One shot has no shared specification files and stores its prompt once; multi-step has at least two primary task files. Hash mode, all defining file bytes, task order, baseline paths and executable flags. Preserve the v1 reader, writer, reference closure, descriptor/manifest bytes and hashes exactly, with no implicit upgrade; v1 templates retain a visible legacy multi-step interpretation, including one-task legacy definitions. Preserve the default inventory's original seven tasks and v1 identity, including the existing policy based on results on the current default revision. Every attempted competitor task requires a commit under the frozen protocol and legacy boundary below. Manual authoring, inspection, capture and approval remain available without Git or an installed harness. TUI/CLI creation, launch review, retained stage counts/evidence, reports and ZIP exchange expose the same modes, ordered inputs and portable snapshot provenance. Require byte/order, dirty/non-Git/subdirectory, source-preservation/change, no-planner, v1/v2 compatibility and offline round-trip tests across the two benchmark types × two target modes.

### Required task commits

Every attempted competitor task, including one-shot `T1` and each multi-step task, must end with at least one new competitor-created Git commit containing all deliverable changes in scope; a task with no file changes still creates an explicit empty milestone commit. Follow the binding [mandatory task-commit contract](../BENCHMARK-MODES.md#mandatory-task-commits). Approval freezes the versioned `required_per_task` policy, common instruction bytes, executable check source/version and deliverable-scope rules in the existing canonical execution-protocol payload and reference closure; authored prompt/spec bytes and logical task counts remain unchanged. Git is required before competitor execution, while manual authoring, inspection, capture and approval require neither Git nor a harness. For new-policy trials, M05 prepares independent isolated repositories: an empty baseline starts with unborn `HEAD` and no setup commit; a populated baseline gets one synthetic setup commit matching admitted paths, bytes and executable flags, excluded from competitor counts. Never reuse source Git internals or mutate the original folder; isolate Git identity, personal configuration, hooks, signing and interactive requirements without changing user settings or pushing. Capture each attempted task's start/end repository and snapshot evidence; the end tip must advance with new reachable commits, preserve the start tip and every retained preceding stage tip as ancestors, and match all in-scope delivered bytes, deletions and executable flags without staged, unstaged or untracked deliverable changes. Ignore rules cannot hide required deliverables. Observed missing commits, invalid advancement, rewritten prior stages or dirty deliverables are `FAIL`; unreadable or missing history/snapshot evidence is `UNVERIFIED`, separately from process outcomes and application checks. Check the protocol even when authored checks are empty; never commit for the competitor, add a repair invocation, or let a later commit repair an earlier stage. Retain scoped policy/check versions and digests, start/end and setup/task commit identities, ancestry, inventories, snapshots and immutable repository evidence through results, reports and ZIP exchange; Git ids are evidence, not template identity. Preserve legacy v1 bytes, hashes and retained outcomes without retrofit or regrading. New launches of incompatible legacy definitions require an explicitly reviewed revision. The built-in inventory retains its exact original M09 branch: no repository before T1, competitor initialization and first commit during T1, then unchanged original advancement checks; do not preinitialize it or strengthen its historical predicates.

### Default inventory benchmark

Ship the existing inventory website specification and task prompts as the default built-in template. It requires HTML5 and vanilla JavaScript, no frameworks or runtime libraries, localStorage persistence, and direct opening of the application's HTML file in a browser. Start from an empty project, not one of the historical generated applications.

| Task | Deliverable |
|---|---|
| T1 | Initialize Git, scaffold the project, write a README, and commit. |
| T2 | Add products, stock, persistent storage, and first-run sample data; commit. |
| T3 | Add inventory viewing and product creation, editing, and deletion; commit. |
| T4 | Add inventory lookup; commit. |
| T5 | Add a persistent cart with quantity changes, removal, and totals; commit. |
| T6 | Complete checkout, update stock, preserve order history, and update the README; commit. |
| T7 | Test in a real browser, fix defects, and commit. |

Preserve the existing task prompt text. Bundle versioned acceptance checks and the web grading rubric with the template so it is ready to run without LLM planning. Editing tasks, checks, baseline files, or rubric creates a new template revision. A six-task variant is a different template, not the default seven-task benchmark. Historical runs must not be assigned a verified matching hash based only on their names or reported task counts.

When an application upgrade ships a newer built-in inventory revision, an installation with no results on its current default revision moves the default to the newest built-in revision. An installation with such results keeps its current default, and the library offers the newer revision with what changed, a note that results from the two revisions cannot be compared, and an action to make it the default. All built-in revisions remain available.

### Workflow

1. **Open the library and inspect the environment.** Show the inventory benchmark as the default choice and detect harnesses, model information, authentication readiness, runtimes, browser support, and hardware collectors. With no supported harness installed, show an actionable error for local planning/execution and prevent those operations; manual template authoring, target inspection/capture, approval, library browsing, ZIP exchange, and saved-result reporting remain available.
2. **Choose or create a template.** Select an approved built-in/imported/custom template to reuse its frozen tasks. To create a new template, choose one shot or multi step independently of the supported software domain, select a current target directory, and review its derived empty/populated target mode and capture. Supply the exact one-shot prompt or an explicitly ordered list of at least two primary specification files; review approved checks, protocol, services, dependencies and rubric before approval. Optional idea-to-plan generation is a separate route.
3. **Optionally plan multi-step work from an idea.** Only when the user chooses generation, select a planner harness/model/effort with a valid previous choice preselected; otherwise use the first usable harness in registry display order: Claude Code, Codex, Grok CLI, Pi, Cursor CLI, OpenCode, with discovered model/effort defaults. A harness whose readiness is undetermined is never preselected or run for planning. If no harness is usable, show an error with a verification action that, with the user's consent, makes one minimal headless call per harness to confirm login and headless operation, records the outcome, and then preselects the first usable harness. Preselect the harness's own default model when the catalog knows it; otherwise the user must choose one, because the planner never runs without an explicit model. Generate common context, ordered primary task files, acceptance checks, and setup/start/stop instructions. Default this optional route to seven tasks including final verification/fixes, with at least two required; review, edit, or regenerate before approving and saving the template. One-shot authoring, manually supplied multi-step files and existing-template reuse skip this step and require no planner.
4. **Configure this benchmark.** Load its saved configurations or select harnesses and provider/model/effort combinations. Allow multiple entries per harness. Every configuration names an explicit model. Default to clean settings, with current settings available. Show the full run setup before execution.
5. **Configure judging and weights.** Independently select `harness_review`, `decision_rubric` or `human_review` as the grading backend and configure its judge, versioned decision profile or human reviewer/form policy. Harness judging remains the default; existing saved harness selections retain their behavior. Preselect a valid saved selection, then, for harness judging, the planner configuration if one was used, otherwise the first selected usable configuration. Select the context-monitoring decision profile independently. Use the template's rubric, choose quality and ranking weights, and complete these choices before launch.
6. **Execute and observe.** Run the configurations against the pinned template revision, show progress and measurements, preserve evidence, and execute its approved checks.
7. **Judge and compare.** Review each delivered artifact and view accumulated results for the same template, including compatible imports from other machines. Generate/open the HTML report.
8. **Exchange work.** Export the template as a ZIP for another machine. Import that machine's result ZIP into the matching benchmark only after template and package integrity checks pass.

Selection defaults are conveniences, not recommendations about model quality. The same approved task suite and grading profile apply to every configuration within a comparison.

## 3. TUI and execution interaction

The TUI is the central place for setup, observation, and results. It provides keyboard navigation, visible shortcuts, mouse interaction, clear validation messages, and layouts that adapt to terminal size.

| View | Required behavior |
|---|---|
| Home/library | Choose the default inventory benchmark, create or import templates, manage revisions and saved configurations, reconnect to active runs, and inspect accumulated results. |
| Environment | Show discovered capabilities, unavailable prerequisites, installation/setup guidance, and a recheck action. |
| Setup | Edit a template's run configurations and judge/weight selections; create or revise task templates separately. |
| Execution | Show harness panels, queued/running/completed states, current tasks, elapsed time, logs, and available measurements, plus a live view of one configuration's current task. |
| Results | Inspect local/imported results, machine and judge filters, evidence, rankings, alternative weights, and ZIP/HTML export actions. |

Derive live panels from the registry and selected harnesses. Preserve a 2×2 arrangement when four panels fit; for five or more, including all six supported harnesses, use a responsive arrangement or list/detail layout that exposes every selected harness with keyboard and mouse navigation, and use list/detail on smaller terminals. Never cap observation at four or five. Logs must be scrollable and searchable; selecting a configuration reveals its task-level details. A live view of a selected configuration shows its current task with the model and effort, the code being written in its workspace, the reasoning the harness exposes, instantaneous output tokens per second, and context use, each labelled with its source. Native values that the harness does not expose remain unavailable. Instantaneous live rates remain advisory, are not retained as benchmark measurements and do not affect rankings; retained Gen tok/s uses the separate matched-request accounting contract in §5. Capture and retain context evidence with native-source, classification, token-count, and context-membership provenance kept separate. Watching and context classification never send input or decisions to the harness.

Default scheduling runs one configuration per selected harness concurrently, deriving the limit from the registry's unique selected harnesses, including six when all six supported harnesses are selected. Apply this default to new configurations; preserve saved explicit concurrency, including four or five jobs. Additional configurations within a harness queue sequentially, and tasks within a configuration always execute sequentially. Provide a sequential mode through `--jobs 1` and the equivalent TUI setting. Record scheduling and concurrency in the results.

Execution must continue independently of the TUI. Closing or detaching the interface leaves the benchmark running. Reconnecting observes existing work without restarting tasks. Stopping a configuration or the whole benchmark is a separate explicit action that also cleans up its child processes and application services.

During execution, users may inspect, detach, reconnect, and stop work. They cannot alter the frozen prompts, selected models, original weights, or inject implementation hints into an active comparison.

### Command-line access

| Command | Purpose |
|---|---|
| `axbenchmark` | Open the TUI. |
| `axbenchmark --attach RUN_REF` | Reconnect to a running benchmark. |
| `axbenchmark run --config benchmark.yaml --no-tui` | Run a fully specified benchmark with plain terminal progress. |
| `axbenchmark status RUN_REF` | Show persisted status. |
| `axbenchmark stop RUN_REF` | Stop the run and its child processes. |
| `axbenchmark models refresh` | Refresh model and effort discovery. |
| `axbenchmark doctor` | Inspect prerequisites and display setup guidance. |
| `axbenchmark report RUN_DIR` | Regenerate a report from saved results without model calls. |
| `axbenchmark templates export TEMPLATE_SHA --output template.zip` | Export an exact template revision as a portable ZIP. |
| `axbenchmark templates import template.zip` | Validate and add a template to the library. |
| `axbenchmark results export RUN_REF --output results.zip` | Export a run's results and the exact template they reference. |
| `axbenchmark results import results.zip --template TEMPLATE_SHA` | Validate and add results only to the matching local template revision. |

`RUN_REF` accepts a run UID or a label that identifies exactly one visible run. An ambiguous label produces an error listing the candidate UIDs and origins; it never silently chooses a run. The unattended mode requires complete configuration rather than pausing for interactive questions. A disconnected interface must not be treated as an interrupted benchmark; an actual execution failure must remain visible in saved state.

## 4. Models and configuration

Provide a versioned YAML catalog of models and their supported efforts, organized by harness and provider. Model availability and effort support depend on the installed harness, provider, and account; a model's name alone is not sufficient evidence of compatibility.

Each catalog entry identifies the model, display name, supported effort values, known default effort, relevant capabilities such as image input, and optional pricing. Record the metadata source, retrieval date, and applicable harness version. Distinguish known support, unsupported settings, and unknown capability information.

Catalog refresh also records each provider's published prices and each harness's own default model per provider and account, read from the harness's configuration or status output without a model call, with their source and retrieval date under the same precedence. Prices are collected only during an explicit catalog refresh, never during a run. A failed refresh keeps the last valid prices, offline operation uses cached or bundled prices, and the prices in effect are recorded with the run at launch.

Catalog refresh also collects exchange rates to USD for the currencies in which prices are published, recording each rate's source URL and retrieval date. All editable and stored rates use currency units per 1 USD and must be positive; for example, a rate of 4000 COP per USD converts 4000 COP to 1 USD by division, and 1 USD to 4000 COP by multiplication. Rates follow the same rules as prices: they are collected only during an explicit catalog refresh, never during a run; a failed refresh keeps the last valid rates; offline operation uses cached rates; and user-supplied rates override collected ones and are labeled as user-supplied.

Record each account's billing kind as API, subscription, local, or unknown, read from the harness's status output without a model call. Users can declare an account's billing kind as a user override, labeled as declared by the user; a declaration takes priority over the discovered value, and an account with neither is unknown. The billing kind in effect is recorded with the run at launch, and wherever a cost basis is shown, a declared billing kind is labeled as declared.

On first launch, attempt automatic discovery through available harness/provider interfaces. Use a cached catalog thereafter, refreshing when the installed harness version changes or the user explicitly requests it. A failed refresh must preserve the last valid data. Offline operation may use cached or bundled entries with their source and age visible.

Maintain a bundled baseline, a discovered cache, and separate user overrides. Apply precedence in that order, with explicit user overrides taking priority. Refreshes must not overwrite overrides.

Only offer known supported efforts. For unknown effort support, offer a harness-default option and omit an explicit effort argument. Do not guess effort lists or silently substitute a different model after a failure. Record requested settings and effective settings when the harness exposes them; do not claim a requested effort was verified when it was not.

Persist reusable run configurations per benchmark template revision and scoring presets in YAML. A run configuration pins its template SHA-256. Saved result records include that hash, the resolved configuration, machine identity/details, and catalog metadata used at launch. Credentials must not appear in exported settings, logs, or reports.

### Model variants and lineage comparison

Classify competitor results through the binding [model-variant and provenance contract](../MODEL-VARIANTS.md): retain the base checkpoint, fine-tune/adapter/merge lineage, stored and runtime quantization, exact artifact/component identities where exposed, and requested versus effectively served evidence. Fine-tuning and quantization compose; never treat a QLoRA training setting or KV-cache precision as proof of inference-weight quantization. Retain creator roles separately for base author, fine-tuner, quantizer/converter and distributor, and distinguish creation, publication, upload and observation dates with source, precision and uncertainty. Missing facts stay explicitly unknown or declared, not inferred from a filename, uploader or today's date. Content identity remains distinct from lineage/credit/date claims: hashing bytes does not prove their ancestry or author. Freeze selection/provenance with each run and preserve corrections as attributable annotations without rewriting old facts. Compare quant-only, fine-tune and combined variants within the exact same benchmark template SHA-256, using visible lineage evidence tiers and controls for harness/runtime/hardware/settings; cross-machine/imported exploratory comparison remains available with its differences disclosed. Keep complete per-configuration trial groups, judge-group separation, quality grades and all measurement/ranking formulas unchanged; do not pool unrelated runs into a single model score or make a causal claim from matching labels. Surface base/variant, quant/fine-tune, creator-role and date-kind facets in setup, results, CLI and offline HTML/ZIP, including legacy unknowns. Variant metadata belongs to competitor configuration/provenance, not benchmark identity or judge input; automated and human quality judges remain blind to creator/variant metadata. Metadata discovery performs no inference, training, quantization, model loading or unapproved artifact execution; base-model lineage never supplies pricing or a claim of free hosting.

### Same-model comparison across harnesses

Allow users to select one exact model/variant and explicit model-native effort contract, one benchmark revision/baseline and trial count, then generate a controlled comparison across the full supported harness registry: Claude Code, Codex CLI, Grok CLI, Pi, Cursor CLI and OpenCode. Keep one visible cell per harness, with installed-version readiness, model/effort mapping, selected access route and explicit blocked/unverified/not-selected reasons. Strict launch requires every selected cell to satisfy the common model/effort/control contract; choosing a subset or exploratory comparison is explicit and retains incomplete coverage. An unsupported cell creates no fake failure, grade or zero score. Preserve one configuration per selected harness, complete independent trials, existing task commits and the normal scheduler. Native instructions/tools/orchestration remain the intentionally varied harness behavior; matching model names or effort labels does not prove equivalent settings or internal reasoning. Freeze requested mappings, observe actual route/model/effort and helper-call coverage, retain mismatches and measured cost, and stop/exclude affected lanes without silently substituting models or invalidating the shared template. Use the existing exact metrics/rankings and separate judge groups, with a distinct harness-comparison axis rather than weakening strict quant/fine-tune comparisons. The binding [cross-harness comparison contract](../CROSS-HARNESS-COMPARISON.md) defines setup, runtime, normalized retention, API/CLI/design and acceptance.

### Configurable API access routes

Support versioned OpenRouter and LiteLLM API access profiles, including an explicitly declared LiteLLM-to-OpenRouter chain, for supported harnesses, especially Claude Code and Codex CLI. These are provider routes, not new harnesses; validate the selected harness distribution/version, required Anthropic Messages/OpenAI Responses/Chat Completions dialect, upstream model identity, model-specific effort mapping, tool/stream behavior and controlled routing policy before claiming compatibility. Distinguish documentation, declarations, installed qualification and effective runtime evidence; unknown custom routing remains explicit. Configure only benchmark-owned temporary settings/environments without changing personal harness settings or starting/installing a gateway. Credentials stay machine-local references and never enter retained portable data. Keep metadata discovery free of inference; exact-route qualification is a separate bounded, explicitly consented diagnostic with verification accounting. Actual upstream inference locality and route-specific billing/prices govern costs and budget warnings; a local gateway forwarding remote, mixed or unknown inference is not local model execution. Record all exposed billable attempts and correlate duplicate gateway/upstream observations instead of double charging. Persist queryable profiles, hops, mappings, full comparison cells and request evidence in normalized SQLite and portable reports. Roles remain independently selected; ordinary API access does not enable native System One decision grading or context analysis. Follow [CROSS-HARNESS-COMPARISON.md](../CROSS-HARNESS-COMPARISON.md); this is a fresh implementation with no obsolete compatibility layer.

### Existing configured agents and aliases

Allow users to register and benchmark an existing configured agent through a local alias or named launcher profile, such as `claudeg`, while retaining its underlying registered harness identity. Inspect the selected alias/environment/argument declarations and eligible profile settings statically, without sourcing shell startup files, evaluating substitutions or invoking the agent during discovery. Resolve supported declarations to a qualified noninteractive adapter plan so daemon execution does not depend on interactive alias availability. Default to a captured existing-profile treatment; clean treatment or benchmark-only overrides must be explicit and remain distinguishable from the source. Keep personal profiles, authentication, history and session stores untouched, use isolated runtime state and preserve fresh sessions, task/workspace boundaries and role restrictions. Declared model/effort/thinking/context settings are not proof of effective behavior; optional unknown settings may remain visible in an ordinary inherited-profile run, while strict same-model comparisons require the existing qualified controls. Conflicting common targets, dynamic/unqualified wrappers, missing required dependencies or unisolatable behavior remain explicit blockers rather than silent fallback. Freeze versioned sanitized profile/asset/control and treatment provenance; revalidate drift before execution, retain credentials only through local resolution references, and keep portable profile imports inactive. A matrix still has one cell per harness, while ordinary configurations may compare multiple profiles of that harness. Any private configuration referenced during design is illustrative only and must not be copied, bundled, automatically registered, used as a default, or used to seed tests; all fixture values are independently fictional. Runtime profiles require an explicit user-selected registration. Expose inspect/register/select flows, named profile/treatment labels and normalized SQLite provenance under the binding [existing-agent profile contract](../CROSS-HARNESS-COMPARISON.md#existing-agent-aliases-and-launcher-profiles).

### Cursor CLI support

Apply the existing competitor/planner/judge roles, clean/current policies, explicit frozen model selection, supported-or-omitted effort controls and fresh-process/session rules to both benchmark modes and isolated empty/populated captures from Git/non-Git sources, with trial Git preparation governed by the frozen protocol. Follow the [Cursor adapter delivery contract](../M05/08-cursor-adapter.md): verify executable provenance and the exact installed CLI version against current official documentation, implement the complete shared adapter and lifecycle contract, and gate actual capabilities on installed-version/platform tests as well as fixtures. Unsupported or unverified capabilities remain explicit; no documentation edit or fixture alone establishes delivered adapter support or a passing runtime matrix.

### OpenCode support

Register OpenCode as the sixth native harness, `opencode`, after Cursor CLI in the shared registry, discovery, model catalogs, selection, execution and reporting, preserving all existing harnesses and saved explicit settings. Follow the [OpenCode adapter delivery contract](../M05/09-opencode-adapter.md) for competitor, planner, judge and consented verification roles under the existing M05 adapter/lifecycle boundary. Establish executable provenance and installed generation/version before selecting documented V1 or V2 CLI, configuration, permissions, effort and event-parser contracts; never infer generation from the executable name, mix their schemas, invent flags, or claim a permission rule alone provides containment. Use metadata-only discovery/default selection without inference or personal-setting changes; preserve unknown authentication, billing, model and capability facts. For competitor/planner/judge work, require exact frozen model selection, supported-or-omitted effort, evidence for all five clean categories, enforced role protections, and a fresh noninteractive process/conversation for each task or role invocation; unsupported clean controls or unavoidable prompts block the affected launch instead of selecting current mode. Consented verification retains its bounded one-call, no-explicit-model/effort and all-tools-denied exception. V2 additionally requires a version-proven invocation-owned private server/state lifecycle and complete descendant cleanup, without attachment to personal/shared services. Preserve exact one-shot bytes, ordered multi-step input prefixes and isolated workspace continuity, delegating Git setup and required commits to the shared frozen protocol. Retain sanitized native events and honest usage, cost/currency, reasoning, request timing and context evidence, with separate parent/subagent scope and explicit gaps; unavailable values stay unknown, global/session aggregates do not become trial accounting, and neither configuration fallbacks nor fixtures establish verified model capacity or installed support. Gate claimed capabilities on generation/version-specific fixtures and real macOS/Linux lifecycle, isolation, selection and observation evidence; this requirement is proposed work, not a runtime-completion claim.

### Decision engines and grading backends

Provide independently selectable decision profiles for context monitoring and grading through one shared `SystemOneAdapter` and the same `/v1/systemone` API. Support TypeSafe's remote service, including pinned Jev profiles where suitable, and directly addressed compatible local servers, initially Ollama; server dialect differences remain within that adapter. ### Editable weights

Expose two independent weight sets in the TUI and YAML:

- **Quality-category weights** determine the overall application grade.
- **Ranking-factor weights** determine the combined decision score across `cost`, `time`, `quality`, `generation_rate`, `input_tokens`, `output_tokens`, `file_count`, and `loc`. Cost/time directions are fixed `lower`, quality is fixed `higher`; every new factor requires an explicit `higher` or `lower` direction before its weight can be positive, and may use null only at zero weight. Direction expresses user preference and does not change grades. Valid legacy three-key records migrate in memory to five zero weights and null new directions while retaining original schema/bytes/digest; incomplete version-2 maps are errors and sealed records are never rewritten. Zero weight removes a contribution while retaining raw grades and measurements for later analysis.

Alternative weighting or direction changes in the results view or HTML report recalculate totals without model calls, probes, new measurement requests or overwriting original results. Clearly label alternatives, provide reset, and allow exporting the alternative configuration/report.

The quality grade is the weighted mean of category grades. The combined ranking is:

`100 × Σ(enabled k) weight_k × factor_k`, with `contribution_k = 100 × weight_k × factor_k`; when all new weights are zero this is `100 × (cost_weight × cost_factor + time_weight × time_factor + quality_weight × quality_grade / 5)`.

Normalize all eight ranking weights together to sum to one, independently of the six quality-category weights. Quality uses `Q / 5`. Preserve the existing cost/time factors, minimum eligible cost/time divided by configuration cost/time, including the verified-zero-cost policy and guarded zero-elapsed-time state. For a new factor with complete compatible value `x`, direction `lower` uses eligible minimum `m / x` when `m > 0`; when `m = 0`, proven complete zero receives 1 and positive values receive 0. Direction `higher` uses `x / M` for eligible maximum `M > 0`; if `M = 0`, all eligible proven complete zeros receive 1. These new-metric zero conventions never change cost or time rules. Skip zero-weight factors before lookup, compatibility, extrema or division. Derive every enabled reference from the same eligible population after all gates, recomputing it when filters or alternatives change; preserve exact rational arithmetic for factors, contributions, scores and ordering, rounding only for display.

Default shortlist eligibility requires completed execution, verified required checks, valid required grades, and a raw business rules/specification grade of at least 4/5 in every frozen trial; neither zero quality weight nor metric direction waives those gates. Every positively weighted measurement must then be known, complete and compatible across that full trial roster under an explicit common token/timing/artifact scope and versioned measurement policy. If incompatible candidates have no selected common policy, explain that the ranking is uncomputable instead of silently choosing a favorable subset. Exclude missing, partial or incompatible subjects with typed metric reasons, keys and failing trial identities; do not silently redistribute weights or omit trials. Partial cost excludes lowest-cost and positive-cost combined rankings; partial elapsed time does likewise for time. Keep excluded raw values, coverage and explanations in the tables. Zero-weight components require no measurement and do not impose compatibility checks; with all new weights zero, preserve existing three-component eligibility, scores and exact ordering. Failed, incomplete, and excluded configurations remain in the full tables.

Exclude it from lowest-cost rankings and combined rankings with a positive cost weight, explaining `cost_zero_unverified`; never use it as a denominator or relabel it as a verified charge. A zero cost weight permits eligibility subject to the other gates.

If a verified minimum cost is zero, eligible verified-zero entries receive the maximum cost contribution and positive-cost entries receive zero for that component. Never turn unavailable cost into zero. Report fewer than five entries when fewer qualify, and explain when no ranking can be computed.

## 7. Optional CPU/GPU monitoring

Hardware monitoring defaults to automatic detection and may be disabled. Collect available CPU/GPU utilization, memory, power, energy, and temperature information without making any particular sensor a prerequisite for benchmarking.

The Environment view and `doctor` distinguish missing tools, insufficient permissions, missing drivers/kernel interfaces, unsupported hardware, and collector failures. On macOS and Linux, suggest appropriate installation or setup steps with supporting documentation and a recheck action. Do not automatically install tools or change system permissions. Users can continue with unavailable metrics clearly identified.

Candidate collectors include process/host telemetry through psutil, macmon or powermetrics on compatible Macs, powercap/RAPL counters on Linux, and NVIDIA or AMD vendor tools on supported GPUs. Probe actual capabilities and versions before enabling metrics; installing a utility cannot make unsupported hardware expose a sensor.

For Apple Silicon, the [macmon documentation](https://github.com/vladkens/macmon) provides installation instructions and JSON telemetry support. Linux setup guidance should reference the relevant [powercap documentation](https://cdn.kernel.org/doc/html/latest/power/powercap/powercap.html), [NVIDIA SMI documentation](https://docs.nvidia.com/deploy/nvidia-smi/), or [AMD SMI documentation](https://rocm.docs.amd.com/projects/amdsmi/en/latest/how-to/amdsmi-cli-tool.html). Use verified platform-specific instructions rather than assuming one package command works across distributions.

Collect host telemetry once per experiment. The sampling interval is a run-configuration setting from 0.5 to 10 seconds, defaulting to one second and frozen at launch; reject invalid values. A collector that cannot sample that fast uses its own minimum, and each collector's actual interval is recorded and shown rather than presented as the requested one. Preserve timestamps, device/domain identity, units, source, scope, and coverage. Sampling or collector failures must not stop the benchmark.

### Attribution and limits

- Attribute process-tree CPU time and memory where observable. Do not assume a separately running model server belongs to the harness process tree.
- Label host-wide, CPU-package, GPU, and SoC readings by their actual scope.
- Keep parallel execution as the default. Shared-device energy belongs to the experiment; do not divide it arbitrarily among concurrent harnesses.
- In sequential mode, show energy observed during each configuration's execution windows, explicitly including background activity rather than claiming exclusive attribution.
- For cloud models, local telemetry describes the client machine, not the provider's inference hardware.
- Prefer energy-counter deltas where available; otherwise integrate sampled power and label the result as an estimate. Distinguish wraps from resets using collector continuity/reset evidence, timestamps and plausible bounds; a known counter range alone does not establish a wrap. Ambiguous decreases and missing samples leave uncovered intervals and partial coverage.
- Choose one source for duplicate observations of the same physical domain before avoiding overlaps among package, subdomain and SoC measurements. Preserve the source choice, metric definitions and uncertainty; power estimates are not wall-socket measurements.

An optional electricity tariff can produce a clearly labeled energy-cost estimate. Set the tariff per kWh, with its currency, in the run configuration before launch, where it is frozen with the run. It can also be entered or changed later in results as an analysis setting that recalculates the estimate as a labeled alternative without changing the original record. Do not claim whole-system electricity cost from CPU-package or GPU-only readings, and do not add overlapping energy charges to reported provider costs.

In sequential runs, a configuration on a local model endpoint without API cost uses its energy-cost estimate, the energy measured during its execution windows multiplied by the tariff, as its cost for rankings. Label it as an energy estimate with its measurement scope, such as GPU and CPU package rather than whole system. Shared experiment energy from parallel runs stays separate from per-configuration rankings, so such a configuration's cost remains unknown there. Without a tariff or an energy measurement, its cost is also unknown.

## 8. ZIP exchange and template identity

### Portable packages

A **template ZIP** contains a versioned manifest and the complete frozen v1 or v2 benchmark definition, dispatching by descriptor version: benchmark mode where defined, common specification context, ordered primary task files, starting files/fixtures, acceptance checks, setup/start/stop instructions, execution rules, and grading rubric. Preserve legacy v1 bytes and identity without implicit conversion. Current-folder templates include the actual approved starting snapshot, independent of its originating path or Git availability. Required runtime dependencies are declared; installed dependency directories and credentials are not included.

A **result ZIP** contains the exact template plus the selected run's result records, configuration, prices and exchange rates frozen at launch, machine label and hardware/OS details, harness versions, timestamps, task outcomes, measurements and their coverage, original weights, judge metadata/grades, generated artifact snapshots, and supporting evidence. Include a file-integrity manifest covering the result payload. Do not export raw credentials or unrelated files from the machine. Preserve source run UIDs, result identifiers, trial associations, invalidations and provenance across subsequent exports.

Importing a package is a data operation: it must not run its scripts, install dependencies, invoke a model, or modify an existing result. Executing an imported benchmark or rejudging an artifact is a separate explicit action. Validate archive paths, reject escaping paths and links, and enforce bounded extraction before accepting contents. Reject corrupt, incomplete, or unsupported-format packages with an actionable explanation and without partially adding them to the library. Import visibility is all-or-nothing across templates and results, including during concurrent reads and crash recovery: another client can act on the prior collection or the complete import, never a staged half-import. Failed imports and retries preserve pre-existing records.

### SHA-256 matching

Compute the template SHA-256 from a canonical manifest of its benchmark-defining metadata and payload files, including normalized relative paths and each file's content digest. Define one versioned, deterministic serialization so identical templates produce the same hash on macOS and Linux. ZIP compression, entry order, timestamps, local absolute paths, machine identity, and display-only naming do not determine template identity.

Descriptor version, benchmark mode where defined, shared context, every ordered primary file's exact bytes, task order, checks, required baseline files and their executable intent, execution protocol including its declared task-commit policy/version, common instruction and deliverable scope, and rubric definitions are covered by the hash. Changing any of these creates a new template revision; an explicit v1-to-v2 conversion is a new identity even when its task text is unchanged. Preserve legacy protocol bytes and hash closure without adding an implicit policy. Harness/model/effort selections, clean/current run settings, concurrency, trial count, hardware sampling interval, judge selection, pricing, exchange rates, display currency, electricity tariff, and adjustable scoring weights belong to run or analysis configuration and do not change the template hash. They remain recorded and visible as comparison differences.

On template import, recompute the digest from the extracted definition and verify it against the manifest before registering it. On result import, recompute the digest from the embedded template and verify it against both the package's declared template hash and the selected local template's recomputed hash. Also check payload digests, result-to-template references, and task identifiers against the validated template. A matching name, filename, or declared hash alone is insufficient.

If hashes differ, reject adding the results to the selected benchmark and show the expected and received template identities. The user may instead import the embedded template as a separate library revision and associate the results with that matching revision. Never force-merge mismatched templates or overwrite a template to make an import appear compatible.

Reimporting the same template or identical result is idempotent. Keep distinct runs of the same configuration even when their human labels collide; reject a reused run UID with a conflicting immutable launch binding or a conflicting payload reusing an existing result identifier. Result data from different template hashes never enter the same comparison or ranking.

### Comparability and provenance

A matching SHA-256 establishes that the packaged benchmark definition is identical. It does not independently prove that a third party executed that definition faithfully or that submitted measurements are authentic. Label results as locally produced or imported, retain execution evidence, and describe validation as template/payload integrity verification rather than execution certification.

Within a matching template, display and filter by originating machine, harness/model/effort, environment policy, concurrency, and judge configuration. Machine differences are intentional comparison inputs, not hash mismatches. Apply a common selected weight set when calculating a combined report, retaining each result's original weights and grades. When every result froze the same original weights, use them as the original ranking weights; otherwise use the grading profile's default weights, labeled as profile defaults because the original weights differ across results. Each result's original weights remain visible and selectable as alternative weights, and quality uses the same category weights for every entry in a combined ranking. Preserve cost bases, telemetry limitations, and judge grouping so hash compatibility does not imply identical measurement conditions.

## 9. Reports, retained results, and acceptance criteria

Generate one standalone HTML report using HTML5, vanilla JavaScript, CSS, and embedded chart/data assets. It must work offline when opened by double-click, with no server, CDN, external fonts, framework, or runtime data fetch. Embed screenshots needed to understand the review so moving the HTML alone preserves the report.

### Required presentation

| Element | Contents |
|---|---|
| Measured comparison table | Configuration/artifact, model and effort, originating machine, local/imported provenance, execution environment, verified tasks, elapsed time, Gen tok/s, In tok (cached), Out tok (reasoning), Files / LOC, and cost with its basis. Show pooled/mean labels, units, source, coverage and unknown/partial detail; hardware details are available where collected. |
| Quality table | Raw rubric-category grades, weighted overall grade, judge identity, review evidence, and limitations. |
| Direct top-five chart group | Lowest cost, shortest elapsed time, and highest quality rankings. |
| Cost/time/quality scatterplot | Logarithmic cost axis, elapsed time, quality color, and an environment legend appropriate to the actual configurations. |
| Combined ranking chart | Stacked contributions for every enabled ranking factor with selected weights, directions and reference values; default weights retain the cost/time/quality chart. |

Use the README's presentation as the starting point. Identify the benchmark template and full SHA-256 in every report. The measured table defaults to highest known cost first, unknowns last; the quality table defaults to descending unrounded quality within judge groups. Allow sorting, machine/configuration/judge filtering, and inspection of task details and evidence. Break exact ranking ties deterministically using a stable result identifier so separate runs of the same configuration remain distinguishable.

Show original weights and controls for exploring both alternative weight sets. Update dependent tables, rankings, chart colors, and contributions consistently. Exclude zero costs from the logarithmic plot with an explanation, while retaining them in applicable tables and rankings. Missing data and insufficient eligible entries must produce useful explanations rather than broken charts.

Include optional hardware timelines, measurement scopes, coverage, and setup limitations when relevant. Keep essential tables readable without JavaScript. Safely render generated text and embedded data so prompts, logs, or reviews cannot inject executable HTML.

Persist the approved template and SHA-256, baseline identity, run UID/label, resolved configuration, originating machine/provenance, original weights/directions, raw grades, normalized measurements, task evidence, logs, snapshots, and hardware samples. Before sealing execution facts, finish checks, drain accepted measurement work including request usage/timing receipts, close hardware collection, count the pinned final delivered snapshot, and durably retain final metrics/cost/energy, inventories, policy/source/evidence digests and coverage for every trial with the finalization receipt. Stop/interruption follows the same rule for partial data; storage failures remain visible and cannot claim completion. Sealed execution facts are immutable; reviews and run invalidations are append-only additions. Generate the completion report after the original judging batch finishes. Immediate reports/exports and later imports must agree with retained facts, without relying on unfinished writes. Reporting, ZIP exchange, and alternative weighting must be possible from retained results without new model calls. At completion, attempt to open the report and always display its location.

### Normalized results database

Store all retained result facts, measurements, raw quality grades and calculated quality/ranking scores in an authoritative normalized SQLite database with a documented versioned relational schema, stable identities, scoped foreign keys, constraints, indexes and read-only analysis views. Represent benchmarks/revisions, configurations, machines, model base/quant/fine-tune provenance and creator/date claims, runs, complete expected trial rosters, tasks/checks, measurements, judges/reviews/category grades and derived analysis snapshots as typed related records; multivalued data must not require parsing opaque JSON or duplicate fact rows. Preserve exact values, unknown/partial coverage, immutable sealed facts and append-only reviews/invalidations. Every saved ranking identifies its complete comparison population, selected reviews/judge group, weights/directions, policy and input versions; changing these creates a new snapshot, never silently overwrites an original score. Large evidence remains digest-referenced files. Provide discoverable database location/schema information, consistent snapshots and documented SQL examples for graphs, cost/quality/token analysis and same-benchmark quant/fine-tune comparisons, with explicitly approximate plotting values distinct from exact scores. Imports and review/score persistence are atomic and idempotent even for direct SQL readers; fresh creation starts from an empty database without legacy-data migration or compatibility requirements; future schema upgrades and backups preserve identities/digests. The engine owns writes; external tools may query read-only. Standalone report what-if calculations remain clearly identified unsaved local previews, and original engine-generated score snapshots remain stored. The binding [results database specification](../RESULTS-DATABASE.md) defines the schema, query grains, durability and acceptance contract.

### Acceptance criteria

- A user can complete setup, approve exact one-shot prompts or ordered multi-step files and their required task-commit protocol, observe all selected harnesses including Cursor CLI and OpenCode, inspect results, and export the report through the TUI; equivalent CLI routes enforce the same capture and approval contracts.
- The library includes the unchanged existing seven-task inventory benchmark as the default, runnable without generating new tasks and retaining its original identity and current-default-results upgrade policy. Users can manually create, duplicate, revise, and import other templates without planner calls and save different run configurations for each; idea-to-plan generation remains optional.
- When no supported harness is installed, the application shows an actionable error for local planning/execution and prevents those operations while retaining manual authoring, inspection/capture, approval, library, import/export, and saved-result access. Discovery, offline fallback, unsupported settings, and authentication failures are represented honestly.
- All model work runs headlessly. Multiple configurations per harness, registry/selected-harness-derived parallel defaults reaching six while preserving saved explicit job limits, sequential mode, unattended execution, and reconnecting behave as specified. Cursor CLI and OpenCode pass the same role, isolation, explicit-selection and lifecycle gates with documented and installed-version capability evidence; OpenCode additionally proves its generation-specific private lifecycle where required. Unavailable controls and measurements are never fabricated.
- Detaching or closing the interface does not stop execution; stopping a run cleans up its processes. Interruptions and failures remain recorded.
- Every competitor receives identical approved inputs and an independent baseline per configuration/trial, including eligible dirty/untracked working bytes in Git or non-Git targets without broadening a selected subdirectory. Executable and regular baseline files retain their distinct behavior in local and imported runs while approved storage stays read-only. Original folders, Git state and historical artifacts remain untouched. Failed, partial or stale capture cannot approve; later source edits never alter an approved capture. Template changes detected during the last task, final regression or judging halt the run and exclude all its results, including sealed ones, without rewriting original facts.
- V1 and v2 template ZIP export/import preserves each revision's SHA-256 across operating systems and ZIP repackaging, with unchanged v1 golden hashes and portable execution after the source directory disappears. Modifying benchmark-defining mode, ordered inputs or baseline content changes the digest; choosing different harnesses or machines does not.
- Results from another machine join a benchmark only after recomputed template hashes and result payload integrity match. Mismatches, corruption, conflicting identifiers, and unsafe archives are rejected without partial imports, including under concurrent access or crash recovery; identical repeated imports create no duplicates and preserve prior records. Two machines' same-label/same-configuration runs retain separate trials, means, report scopes and exports.
- Imported results retain their machine/configuration/judge details and evidence. Reports combine only matching templates and distinguish judge groups, measurement conditions, and imported provenance.
- Frozen acceptance checks determine task success. Failed checks, unverified checks, process failures, and judge grades remain distinct. An explicit valid empty suite invents no coverage; required task-commit checks and evidence remain enforced without model-generated checks, engine commits for the competitor or automatic repair tasks. Different conforming inventory implementations pass without a prescribed DOM/storage schema; valid T2 data without T3 UI does not fail prematurely. Every attempted task requires a competitor commit, including an empty milestone when no files change; observed missing commits, rewritten prior stages or dirty in-scope deliverables fail, and unreadable history/evidence remains unverified. The built-in inventory retains its original T1 initialization and advancement checks; legacy bytes, hashes and outcomes remain unchanged. Two trials with different task outcomes retain separate logs, screenshots, check totals and inspectable stage evidence during execution and after ZIP exchange.
- Both weight sets are editable, validated, saved, and reproducible. Eight-factor ranking weights require explicit directions for positively weighted new factors, reject incomplete version-2 maps, and migrate valid legacy maps without rewriting originals. Alternative weighting preserves original grades/results and default three-component scores; shared exact engine and offline JavaScript vectors cover policy compatibility, full-trial eligibility, pooled/mean values, zero extrema, exclusions and reference recomputation. Zero price/energy estimates, unknown billing with positive cost and verified zero follow their distinct eligibility rules and yield finite deterministic rankings. A rate fixture of 4000 COP per USD survives editing, freezing and ZIP exchange, converting 4000 COP to 1 USD and back; missing rates remain unknown.
- Available hardware measurements appear with correct scope. Missing tools produce macOS/Linux guidance; unavailable sensors or permission failures do not prevent a benchmark.
- Parallel runs do not receive fabricated per-harness allocations of shared-device energy. Real wraps, resets with or without a known range, gaps and duplicate sensor sources produce the stated coverage without fabricated energy. Missing and partial measurements are never presented as complete or zero. Delayed accounting and a completed sequential local-energy run produce matching retained, immediate export/report and imported values, with no measurement writes after sealing.
- The exported HTML works through direct-file opening with networking disabled, includes both tables and the three chart groups, and supports alternative weighting without external dependencies.
- All supported software-domain workflows exercise the two benchmark types × two target modes end to end, including empty, dirty Git, non-Git and selected-subdirectory targets. One shot preserves exact prompt bytes and one logical task without planning; multi-step preserves explicit file order, fresh sessions and workspace state without injecting future specifications. TUI navigation/resizing exposes all six harnesses; failure states, portable stage/provenance views and score calculations have verifiable behavior.
