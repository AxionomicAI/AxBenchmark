# Benchmark modes and current-folder baselines

Status: binding implementation contract for new benchmark authoring; proposed behavior, not an implementation claim. Audience: implementers extending the existing library, planning, execution and exchange children. No new module or child node is introduced.

This contract refines the [product baseline](reference/SPEC.md), [M01 definition contract](reference/modules/01-template-library-identity.md#canonical-definition-contract--axbenchmark-definition1), [M16 capture](M16/01-repository-capture.md) and [draft approval](M16/03-draft-approval.md). Where those documents assume every custom template needs a planner, one global specification, or a pinned Git commit, the rules below govern new authoring. Approved legacy definitions retain their original interpretation and bytes.

## Independent choices and execution semantics

| Field | Values | Meaning |
|---|---|---|
| `benchmark_type` | `one_shot`, `multi_step` | How authored work becomes competitor tasks. |
| `project_type` | `frontend`, `backend`, `fullstack`, `mobile`, `devops`, `agentic`, `specification` | Work domain and rubric applicability; independent of benchmark type. |
| `target_mode` | `from_scratch`, `modify` | Read-only projection derived from the approved baseline: empty or populated folder. It is not another serialized source of truth. |

All four benchmark-type × target-mode combinations are valid, for every applicable project type.

**One shot.** The user's authored UTF-8 prompt is the benchmark and becomes exactly one frozen task file and task `T1`. Preserve its exact bytes, including whitespace, Unicode and line endings. An editor's saved UTF-8 bytes are authoritative; prompt-file import preserves the original bytes. Reject empty/whitespace-only or invalid UTF-8 input without silently rewriting it.

Each configuration trial has one logical competitor task and one fresh task session. “One shot” does not mean one model API request: normal harness inference, tools and existing transport retries remain allowed and measured. No automatic planner, prompt paraphrase, task splitting, additional fix task or post-check repair invocation is allowed. Runner instructions supply the already approved execution protocol, including its required commit instruction, without rewriting the authored prompt or adding competitor tasks.

**Multi step.** The regular authoring route takes at least two supplied UTF-8 specification files. One primary file is one ordered task: `N` files produce `N` tasks. Preserve each file's bytes; validate missing, duplicate, unreadable and invalid files before approval. The user reviews an explicit ordered list; filesystem enumeration, upload completion and alphabetic order never determine execution order. Reordering is a defining edit.

The workspace carries state between steps of a trial. Every step starts a fresh process/conversation under [M05](reference/modules/05-harness-execution-isolation.md); the agent inspects the current workspace to continue. The engine-supplied input pack contains approved common context and the introduced prefix through the current step. Previously introduced specifications may remain available; future step files are withheld until their step. This controls supplied benchmark files, not information already present in the baseline or generated workspace: do not claim that existing project content can be hidden.

An optional **idea → planner → reviewed multi-step template** route remains available, with the existing default of seven tasks including its authored final verification/fixes task. New generated multi-step definitions require at least two tasks. Planning is never required for one-shot authoring, supplied-spec import or approved-template reuse. Manual authoring, inspection, capture and approval remain available without an installed harness; local execution still requires the chosen usable harness.

The built-in inventory retains its seven original task prompts, checks and existing identity, including its per-task commits and authored T7 repair task. New definitions follow the mandatory task-commit protocol below; this adds no competitor task or repair invocation.

## Mandatory task commits

**R183:** Every attempted competitor task must end with at least one new competitor-created Git commit in its isolated trial workspace. This applies to one-shot `T1` and every ordered multi-step task, for both empty and populated baselines. All deliverable changes in that task's approved scope must be committed. A task that needs no file changes must still create an explicit empty milestone commit. Tasks never started have no invented commit outcome; an attempted task's process outcome remains separate from its protocol check.

**Frozen contract and exact prompts.** M16.3 approval freezes a versioned `required_per_task` commit policy and common instruction inside the execution-protocol document already referenced by `execution_protocol`. Do not add another metadata field or rewrite the authored prompt/spec bytes. Freeze the policy version, common instruction bytes, executable check source/version, deliverable-scope rules and their reference closure as defining payloads through M01. M05 supplies that approved instruction with each task; M07/M11 freeze and execute it unchanged. One shot remains one logical task; multi-step remains one primary file per step. No additional model call may repair a missing commit.

**Git readiness and isolated setup.** Git is a run-time prerequisite checked before competitor execution, not a prerequisite for manual authoring, inspection or current-folder capture; the source folder may remain outside Git. M05.2 prepares an independent repository per new-policy trial wholly inside its isolated workspace. Never copy, follow or reuse the source `.git` directory/pointer, object store, index, hooks, configuration or remotes; never initialize or mutate the original folder. A new empty-baseline repository starts with unborn `HEAD` and no setup commit, so T1 creates the first commit. Git documents initialization as creating a branch with no commits. [Git initialization](https://git-scm.com/docs/git-init)

For a populated capture, create one synthetic baseline commit representing exactly the admitted relative paths, bytes and semantic executable flags before measured competitor work starts. Retain its identity as engine/setup evidence, exclude it from competitor task-commit counts and do not replace the frozen capture's identity with its Git id. The setup must neither transform captured bytes nor omit admitted files because of ignore rules. Provision disjoint repositories even when trials share a baseline; carry each trial's repository and workspace forward between its fresh task sessions.

Personal Git identity/configuration, inherited Git environment, hooks, signing, remotes and interactive prompts must not affect setup or task commits. Establish explicit benchmark identity and isolated settings scoped to the trial without modifying user configuration; disable inherited personal hooks/signing and interactive requirements, and do not auto-push. Any explicitly authored project behavior remains governed by the frozen protocol rather than silently stripped by these personal-setting controls. Record effective setup and any inability to establish it as a typed readiness/setup failure before invocation. These are required controls for clean and current harness modes alike. The competitor creates its own task commits; the engine may create only the synthetic populated-baseline setup commit. Git supports explicit empty commits (`--allow-empty`) and disabling signing; these capabilities do not authorize engine commits on the competitor's behalf. [Git commit options](https://git-scm.com/docs/git-commit)

**Advancement and complete delivery.** Capture each attempted task's start repository state before invocation and end state after process drainage. The end `HEAD` must identify a new reachable commit absent from the captured start history. For a born start `HEAD`, that start tip and all retained preceding stage tips must remain ancestors of the end tip; amending, resetting or replacing earlier stages cannot satisfy advancement. An unborn start must become a valid first commit. Multiple task commits are allowed; no fixed commit message or nonempty diff is required. The end commit tree must match all delivered paths, bytes, deletions and executable flags in scope, with no remaining staged, unstaged or untracked deliverable change. A later task's commit never repairs an earlier missing or invalid milestone.

Use the frozen snapshot/deliverable scope and actual filesystem inventory to assess completeness. `.gitignore`, local/global excludes or a clean default Git status cannot hide a required deliverable; Git status omits ignored files by default. [Git status](https://git-scm.com/docs/git-status) Retain included/excluded path inventories and reasons. VCS internals, engine evidence and declared dependency/cache paths stay excluded under the same versioned scope rules as [Files / LOC](BENCHMARK-STATISTICS.md#final-delivered-files-and-physical-loc); these exclusions cannot remove otherwise required deliverables.

**Verification and evidence.** M08.1–2 executes the frozen mandatory protocol check after every attempted task even when its authored acceptance suite is explicitly empty. An observed missing commit, invalid advancement, rewritten prior stage or uncommitted in-scope change is `FAIL` (`failed/application_failure`); unreadable or missing history/snapshot evidence is `UNVERIFIED` with its actual cause. Keep application checks and process outcomes separate. A protocol pass proves commit compliance, not invented behavioral coverage. Preserve all available artifact snapshots, logs and failure evidence; never auto-commit, silently retry the task or invoke a repair agent. M11 applies the existing continuation/stop policy and M06's existing outcome rules without inventing a ranking penalty.

M05/M08 evidence binds `ResultId`, `TrialRef`, task id and `InvocationId`; retain start/end `HEAD` (including explicit absent/unborn state), commit/tree ids, newly reachable commit ids, the preceding retained tip, setup-versus-competitor origin, snapshot/digest references, ancestry observations, scoped dirty/untracked paths and inclusion/exclusion reasons. Commit timestamps do not establish task timing or attribution; use the retained invocation boundaries and repository observations. Git ids remain evidence, distinct from the template's canonical SHA-256 identity. Retain policy/check version and digest, observed values and classification through M02's durable idempotent writes. Recovery replays retained writes without creating commits or rerunning competitor work. M13 reports and M17 exchange preserve the same scoped facts and sufficient immutable repository evidence to inspect the declared observations after the source/workspace disappears; optional display metadata cannot substitute for executable evidence.

**Legacy boundary.** Existing v1 definitions, prompt/protocol/check bytes, hashes and retained outcomes remain immutable: no silent retrofit, regrade or rehash. A new launch of a legacy definition without a compatible declared per-task commit protocol requires an explicitly reviewed new revision before execution. The built-in inventory already declares per-task commits and retains its exact legacy acceptance branch: no repository before T1, competitor initialization and first commit during T1, then its original commit-advancement checks. Do not preinitialize that legacy workspace or strengthen its historical predicates. Only new-policy definitions use the empty/populated setup rules above; the mandatory rule does not authorize changes to M09's original package.

## Current-folder inspection and immutable capture

The user selects an existing readable directory. It may be empty, populated, outside Git, a Git worktree or a subdirectory inside one. The selected directory is the capture root; discovering a Git root must not broaden it. Git is optional for inspection/capture, while execution requires Git under the mandatory task-commit protocol. Inspect actual current filesystem entries, not `HEAD`, a selected commit, or the Git index.

For admitted regular files, capture current working-file bytes, including eligible tracked, modified, staged and untracked paths. If the index and working file differ, the working file wins. A staged deletion with a current file still captures that file; a missing current file is absent. Binary baseline files are supported.

The original directory is read-only to AxBenchmark throughout inspection, capture and execution: no checkout, stash, clean, reset, commit, initialization, chmod, source writes or copy-back. Engine staging must be disjoint from the selected tree. Every configuration/trial receives an isolated writable copy of the same completed immutable capture; no competitor runs inside the original directory.

**Emptiness precedes admission/exclusion.** A versioned administrative-entry policy ignores VCS internals (`.git`, `.hg`, `.svn`, including metadata pointer files) and standard OS metadata (`.DS_Store`, `Thumbs.db`), without following them. The exact administrative policy is shown with inspection provenance. Root and nested empty directories alone contain no project content. Any other file or unsupported entry establishes nonempty content, even when unreadable or subsequently excluded. Inspection failure yields an actionable error, never an inferred empty folder.

Thus no meaningful content means `from_scratch`; nonempty content means `modify`. Apply the existing portable exclusion policy afterward. Enumerate actual exclusions and reasons before approval, including VCS metadata, credential material and installed dependency/cache directories; show eligible counts and admitted bytes as well. Do not blanket-exclude untracked files or use Git ignore rules as the capture definition. A nonempty folder with no admitted regular files is an actionable `baseline.no_admitted_files` error, not a silent scratch benchmark.

Unsupported links/special entries either fail with the exact relative path or require an explicit reviewed exclusion. Never follow a symlink, resolve an external target into the snapshot, or let an unsupported entry masquerade as an empty directory. Reuse M01 path normalization and case-fold/file-directory collision validation before materialization. Exclusions must not silently remove a declared required input.

Capture uses engine-owned safe staging and a deterministic inventory of relative paths, entry types, content digests and semantic executable flags. Compare the source pre-copy inventory, copied bytes/modes and post-copy inventory; publish only when they agree. A changed file, path roster or mode causes bounded retry or typed `baseline.source_changed`. Partial, cancelled or failed captures never become `baselineReady`.

These comparisons are consistency evidence, not a claim of an atomic filesystem snapshot; implementations must state that limit. For current POSIX files, `executable` is true when any source execution bit is set; capture it before making stored copies read-only. Keep source paths, timestamps, Git labels/status and capture provenance outside canonical identity. Hash admitted relative paths, bytes and semantic executable flags; do not hash physical read-only storage modes. Restore flags through [M01/M05](M05/02-isolation-observation.md) into isolated copies.

Inspection/capture tokens bind the reviewed source inventory, exclusion policy and draft version. A changed inspection or concurrent capture cannot approve a stale preview; return the changed facts and require an explicit recapture/review. Approval binds exactly one completed snapshot. Thereafter runs, retries, reuse and ZIP imports consume packaged bytes, never refresh from the source path. A requested refresh creates an explicitly reviewed new draft/revision; unchanged canonical content still follows existing duplicate-identity rejection.

## Minimal canonical v2 migration

[M01.1](M01/01-canonical-definition.md) remains the sole `DefinitionCodec.write/read` owner. Add a strict `axbenchmark-definition/2` schema; dispatch by descriptor version. Keep the v1 reader, writer, reference closure, manifest bytes and golden hashes exactly unchanged. Unsupported versions, unknown keys and duplicate keys remain errors. No implicit upgrade or rehash of an approved v1 revision is permitted.

The v2 descriptor is the existing complete v1 field set with precisely these replacements/additions:

| Field | v2 contract |
|---|---|
| `format` | Required literal `"axbenchmark-definition/2"`. |
| `benchmark_type` | Required `"one_shot"` or `"multi_step"`. |
| `shared_specifications` | Required unique array of `RelPath`, replacing singular `specification`; empty is valid. Each entry has existing payload role `specification`. Treat as a set, canonicalized by UTF-8 path order. One-shot requires `[]`. |
| `tasks` | Same ordered `{task_id, prompt_path, check_ids}` objects and existing `task_prompt` role. Each `prompt_path` identifies exactly one primary step file; ids/paths remain unique. One-shot requires exactly `T1`; multi-step requires at least two tasks. Preserve task/check order. |
| `baseline` | Required `{kind: "empty" \| "folder", files: [{path, executable}, ...]}`. Empty requires `[]`; folder requires a nonempty admitted file set. Existing `baseline/` prefix, ordering, role and executable semantics apply. |

The remaining required fields are unchanged: `project_type`, `acceptance_checks`, `execution_protocol`, `services`, `rubric` and `dependencies`. Their owning validators, explicit empty documents/arrays and reference-closure rules still apply. Do not omit these fields because no planner ran.

No new payload role is needed. Store the one-shot prompt once as `task_prompt`; do not copy it into a second global specification. The logical specification view is shared files plus all ordered primary task files, each once. This view is derived from `metadata.json`; no independent serialized definition or specification index can compete with it.

Text bytes remain unnormalized. Mode, task order, exact task/common-context bytes, checks, protocol, rubric and baseline bytes/flags participate in identity through the canonical descriptor and manifest. A one-shot task and a legacy one-task v1 definition are not interchangeable identities. Outer `axbenchmark-manifest/1` and ZIP format versions need not change merely because the descriptor adds v2; M17 dispatches the embedded definition version.

New manually authored and newly planned definitions use v2 and current-folder capture. Legacy v1 project-specification-plus-task definitions project as `multi_step` with a visible legacy marker, including v1 definitions containing one task; never label them one shot. Preserve approved v1 pinned Git baselines, including their allowed zero-file repository shape. Legacy commit capture exists only to maintain that legacy route, not as the new current-folder selector default.

An explicit upgrade or recapture produces a separately reviewed versioned revision and a different comparison identity when its payload changes. Even content-equivalent v1 → v2 upgrades change descriptor bytes/hash and are not same-hash comparable. Existing results keep their original hash. [M09](reference/modules/09-default-inventory-benchmark.md) keeps its existing v1 package, prompt bytes and hashes; the current default-upgrade policy based on results remains unchanged.

## Approval, verification and client behavior

Manual creation stages the prompt/spec files safely into engine-owned storage and retains their explicit order; source upload paths are provenance. Switching benchmark type requires an explicit user action and clears or validates incompatible draft inputs visibly. Do not transform a one-shot prompt into a planner request or silently collapse multiple files into one shot. Target mode is reported from inspection/capture; a manual override cannot falsely mark a populated target empty.

Extend M16's typed inspection projection with source kind, derived target mode, eligible/admitted file counts, exclusion inventory/policy, change stamp, problems and `can_continue`. The durable baseline-capture stage of a planning or manual-creation job returns a complete snapshot reference/digest only after the capture barrier. Preserve existing M11 job/event and optimistic-version rules. Manual creation/draft routes must not depend on planner readiness or instantiate a planner; existing generation/regeneration APIs remain optional and explicit.

Approval still uses [M16.3](M16/03-draft-approval.md)'s canonical conversion, completeness validation and publication transaction. Reuse approved verification/service/rubric profiles or accept explicit authored definitions; review their exact frozen content. Never invoke a model to invent missing checks as a side effect. A valid empty check suite is explicit and conveys no invented behavioral coverage.

Checks, final regression and grading are separate engine phases, not competitor tasks. An empty task-specific suite does not waive required protocol checks or evidence. For grading, approval requires the applicable [M08](M08/01-verification-runtime.md)/[M12](M12/01-review-contract.md) final-artifact evidence declarations: web retains both required viewports, native mobile uses its frozen target/state capture matrix, and other domains use their approved evidence/modalities without an invented screenshot requirement. Execution must actually capture the required final-artifact evidence. Missing runtime evidence stays unverified/ungraded with its cause. An arbitrary prompt does not guarantee a gradable result. Judges never repair the artifact or add tasks/checks.

M07 launch review and M11 scheduling derive task counts from the frozen definition: with `C` configurations, `T` trials and `N` tasks there are `C × T × N` logical competitor tasks, where one shot has `N=1`. Existing budgets, failure/stop policies and separate auxiliary accounting remain intact. Transport retries do not add benchmark tasks. Fresh trial workspaces and per-step sessions remain mandatory.

M05 retains manifest/file-diff evidence alongside the mandatory repository observations, including captures originating outside Git. Every stage names its primary file/task, start/end repository state and resulting snapshot, including `T1` as the final competitor stage for one shot. An unavailable display commit id cannot waive the mandatory check or erase retained artifact evidence.

M01 template summaries/get/tasks expose benchmark type, project type, ordered primary files, shared context, baseline kind and derived target mode. M02/M11/M13 retained results, filters, progress and reports expose the same approved mode and snapshot provenance without treating the absolute originating path as portable identity. Legacy markers remain visible; imported snapshots stay inspectable after the original directory disappears.

M12 consumes the whole-definition specification view and final delivered evidence without requiring a singular global specification file. Keep one independent grading assessment per trial, existing rubric applicability/anonymization and the prohibition on competitor measurement inputs. [Gen/Tokens/Files measurements](BENCHMARK-STATISTICS.md) retain their current meanings across `N` tasks; task count is not API-request count.

Proposed curated CLI forms are `axbenchmark templates create --type one-shot --prompt …` or `--prompt-file PATH`, and `axbenchmark templates create --type multi-step --spec FIRST --spec SECOND …`, each with `--project-type` and `--target-dir`. Repeated `--spec` order is authoritative. Flags and route registration belong to M14/M16; these examples do not claim a current executable command. Inspection, exact-input review, profile validation, capture and approval cannot be bypassed by CLI defaults.
