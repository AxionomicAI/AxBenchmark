# Suggested development sequence

This is an implementation schedule for the 69 children under 18 ownership parents, not a new product requirement or evidence of completed software. [SPEC](reference/SPEC.md) is the product authority; [ARCHITECTURE](../ARCHITECTURE.md) fixes the executable boundaries. Module numbers identify owners: **M01 → M18 is not a whole-module dependency chain**. The [recommendations](reference/recommendations.md#4-correction-and-delivery-order) supply the decomposition rationale, including F15.

**Start coding with [Bootstrap](BOOTSTRAP.md).** It creates the package/test layout, publishes owner schemas/Protocols and proves smoke/import boundaries. The next recommended children are **M11.1 → M11.2 → M15.1 → M15.2**. Early M01/M03 services can then use the real InProcessClient/registry/jobs, and their screens can use the shared fake-client harness and shell. M15.1 includes the presentation-only compact RunListDetail; M11.5 later supplies real run actions.

## Graph and completion semantics

[dependencies.json](dependencies.json) is the machine-readable schedule: exactly **70 nodes (Bootstrap + 69 children)**, each with `id`, spec-root-relative `path`, `requires`, `contracts` and `integration_gates`. `recommended_order` and the table below enumerate every node once in a valid topological order. The graph currently has **315 explicit prerequisite edges**, including Bootstrap edges and intentionally retained direct prerequisites already reachable transitively.

- `requires` names completed child implementations needed to accept the whole consumer child. Every child requires Bootstrap. No parent IDs, screen names, adapter-capability guesses or integration-gate labels are graph nodes.
- `contracts` names the published schemas/Protocols that may be represented by the child's declared strict fixtures. Bootstrap publishes them at the owner's paths before the producer implementation. Available contract ≠ completed producer; data from fixtures proves only the tested contract/orchestration behavior.
- `integration_gates` records the required real-provider, later-consumer and platform checks. These obligations are tracked alongside child completion, **not recursively expanded into prerequisite edges**. A child may finish its bounded implementation with explicitly deferred later-parent gates still open; mandatory local/service checks in its acceptance section remain required. A parent is accepted only after all its children and real integration gates pass.
- Source-format, installed-version, consent, browser and hardware conditions remain explicit external test/implementation gates in the child. A graph-ready node is not proof that those conditions are met. Missing access or an untested platform is pending/unverified, never a passing skip or evidence of provider support.

The child's Entry conditions and ownership are authoritative if this index drifts. Fix both the owner specification and manifest when resolving a genuine contradiction; do not hide one by weakening a `requires` edge or relabelling a mandatory service as a fixture.

## Selecting and finishing a child

1. Read the node, its parent, ARCHITECTURE, exact owned paths, Entry conditions and acceptance/gate sections, plus the binding [context-monitoring extension](CONTEXT-MONITORING.md) for its allocated owners. That extension adds capture/count/classification/retention and client work to existing children; its acceptance and proposed files supplement their local lists without adding graph edges. Load the evidence for every `requires` entry. A spec file existing or a previous agent saying “done” is not completion evidence.
2. Select the first unfinished node in `recommended_order` whose required implementations have passed their required child checks. If an external condition blocks it, record the exact missing documentation/access/host and select the next ready child. Do not create placeholder implementations to mark an edge satisfied. Bootstrap has no implementation prerequisite and is the initial ready node.
3. Work in the child's owned files. Publish/add to shared declarations in their existing owner files; coordinate additive registry/composition/style edits and preserve other work. Feature owners implement their own screens. M15 supplies the shared shell and final integration; M17 owns exchange destinations. No private client, job runner, measurement converter or duplicate DTO may bypass those boundaries.
4. Run the child's specified tests plus the shared contract/import checks touched by the change. API children use actual M11 clients/serialization/dispatch after foundations; screen children use M15's actual fake-client harness at 120×40 and 80×24; provider adapters run the recorded-output and applicable real tests their child requires. Run relevant integration gates as soon as their real providers are ready. Paid/consented verification obeys the owner's explicit consent contract.
5. Record a handoff with child ID, changed owned files, exact commands/results, required runtime/service evidence and remaining gates. For each open real gate identify its scenario, provider/child, platform/version, absent prerequisite or access, and next test. Keep fixture, local-process, installed-provider and supported-host evidence distinguishable. Record downstream parent requirements still pending in [TRACEABILITY](../TRACEABILITY.md); requirement references and unchecked test plans are not passes.
6. Mark the child implementation ready for dependants only when its bounded acceptance is met; any explicitly deferred later-parent gates remain visible. Mark a parent complete only after all children **and** its real cross-module/provider/platform gates pass. If a mandatory child check remains unrun, record the child as pending and do not use it as a completed prerequisite.

A machine selector can evaluate `all(dep in completed for dep in node["requires"])`, using actual verified child completion records. Sort the candidates by `recommended_order`. `contracts` and `integration_gates` are not input to this readiness calculation; inspect them separately for the local task and parent acceptance. Never infer `completed` from this manifest's ordering or from passing fixture tests alone.

## Final acceptance gate

Run the complete source acceptance suite on **macOS and Linux** after child implementation, including all supported harness integrations and no-harness/offline states. Validate simultaneous/sequential scheduling and repeated trials; terminal resize/navigation; detach survival; explicit stop during execution, finalization and judging; engine loss/recovery; template mutation at every detection boundary; frontend/backend/fullstack and current-folder and legacy committed-baseline workflows.

Verify same-template identity across operating systems/repackaging, executable baseline restoration, same-label distinct run subjects, unsafe/corrupt/conflicting ZIP rejection and one-marker publication under faults/concurrent readers. Preserve originals, append-only reviews/invalidation and frozen evidence. Report/ZIP/retained queries must agree after delayed measurements, telemetry close, review settlement and retention; error states must stay recoverable without replaying model work.

Check exact scoring and offline JavaScript parity, every-trial eligibility, judge groups, verified and unverified zero, partial/unknown costs and currency/rate direction. Prove optional telemetry attribution, source/reset/gap limits and retained energy cost before any energy-ranked result. Open exported HTML directly with networking disabled, change both weight sets and regenerate reports without model calls. Confirm UI/CLI consent, capabilities, UID/trial addressing and typed errors agree.

Close all child/parent gates in [the coverage ledger](../TRACEABILITY.md), listing actual test evidence and any unverified provider/platform separately. A pending supported-platform or required provider gate keeps final acceptance pending; neither fixture success nor completed documentation can substitute for it.
